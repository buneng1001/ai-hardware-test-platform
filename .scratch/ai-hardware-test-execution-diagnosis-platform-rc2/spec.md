# 智能硬件测试执行与诊断平台 RC2

Status: ready-for-agent
Version: v0.1.0-rc.2

## Problem Statement

v0.1.0-rc.1 已经跑通了洁净重写项目的基本链路，但测试工程师在使用、复核和交付证据时仍会遇到一组相互关联的问题：
主要能力集中在一个长页面，实际测试文件不能导入，多模型服务边界不清楚，IMU 与时间数据契约不够完整，逐帧视频—IMU
关系无法复核，任务生命周期可能误删证据，模型失败信息也可能泄露内部异常。

RC2 需要在不改变洁净重写边界的前提下，把这些已经确认的修改统一成可实施、可验证的正式规格。平台必须继续保证合成数据、
确定性检查、时间分析、判定和原始报告不依赖 AI；AI 只能提供独立的诊断运行。合成型数据与导入型实际测试数据都必须保留可追溯的
原始证据，任何派生结果都不能覆盖原始事实。

## Solution

将平台整理为清晰的测试工程师工作流：仪表盘、新建任务、根据导入生成、已保存任务和运行详情作为明确页面或标签，设置入口位于顶栏。
测试工程师既可以创建合成型采集任务，也可以在独立的“根据导入生成”页面导入一个实际测试 ZIP，经安全和结构校验后创建导入型采集任务。

RC2 支持硅基流动、DeepSeek 和 Kimi。每个服务商独立维护凭据、端点和模型目录，连接测试和错误反馈明确标识服务商与模型。快速模式使用 100Hz IMU，自定义模式仍允许 50Hz；合成数据生成器升级为六轴 IMU。

所有合成与导入数据都保留原始设备时间和相对时间。时间对齐只产生独立的派生结果。完成时钟对齐后，平台以每一路视频的每一帧为基准，从 IMU 序列选择时间差最小的样本，并输出带双方时间、真实时间差、容差和匹配状态的逐帧映射文件。

合成型和导入型任务共享运行、检查、人工结果、诊断和报告能力，并遵循同一证据保护生命周期：从未执行的任务可以删除，已经有运行记录的任务只能归档。
原始视频可单独下载；证据 ZIP 默认排除原始视频，只能显式包含受限小样。导入流程按已确认的 ZIP、manifest、校验状态机、安全、去重、
不可变数据和临时文件生命周期执行。

## User Stories

1. 作为测试工程师，我想在仪表盘查看运行统计、近期失败和诊断状态，以便快速判断平台和测试结果。
2. 作为测试工程师，我想通过明确的页面或标签进入仪表盘、新建任务、根据导入生成、已保存任务和运行详情，以便理解当前工作位置。
3. 作为测试工程师，我想从顶栏进入设置，以便配置 AI 服务和查看本地数据状态。
4. 作为测试工程师，我想在宽屏和窄屏下看到清楚的页面标题、字段组和按钮组，以便不因布局混乱误操作。
5. 作为测试工程师，我想在新建任务页面创建合成型采集任务，以便继续使用可重复的虚构设备数据。
6. 作为测试工程师，我想按场景优先选择配置项，以便只看到与当前场景相关的参数。
7. 作为测试工程师，我想使用快速、标准或自定义模式，以便在演示速度、覆盖范围和参数控制之间取舍。
8. 作为测试工程师，我想看到预设摘要中的视频参数、IMU 采样率、随机种子和实际/虚拟时间来源，以便知道任务实际会生成什么。
9. 作为测试工程师，我想让快速模式使用 100Hz IMU，以便快速演示仍具有足够的传感器采样密度。
10. 作为测试工程师，我想在自定义模式选择 50、100、200 或 500Hz IMU，以便覆盖不同采样密度；50Hz 不因快速模式变更而被禁止。
11. 作为测试工程师，我想配置视频路数、分辨率、帧率、容器、H.264 编码和码率，以便复现可核验的视频采集条件。
12. 作为测试工程师，我想在保存任务前得到清晰的参数边界和文件规模校验，以便非法或过大的任务不会进入执行队列。
13. 作为测试工程师，我想看到基于场景的任务名称建议，并能保留自己的名称，以便任务容易识别且不限制我的命名。
14. 作为测试工程师，我想知道编号和重名检查的作用域，以便区分同名任务和同一任务的多次运行。
15. 作为测试工程师，我想在判定模式帮助信息中区分正式规格、工程目标和版本基线，以便不把摸底趋势误认为合格结论。
16. 作为测试工程师，我想看到失败检查阈值的统计范围和作用，以便理解超过阈值如何影响判定。
17. 作为测试工程师，我想在保存前看到错误而不产生任务，以便修正输入后再提交。
18. 作为测试工程师，我想在“根据导入生成”标签页看到实际测试 ZIP 的结构、必需文件、大小限制和示例，以便准备合法输入。
19. 作为测试工程师，我想一次选择一个 ZIP 文件导入，以便平台拥有明确、可去重、可追溯的输入边界。
20. 作为测试工程师，我想在未选择 ZIP 时只能点击“导入实际测试文件”，以便不执行没有输入依据的校验或建任务操作。
21. 作为测试工程师，我想在导入后点击“校验导入文件”，以便先确认安全性、结构和平台兼容性。
22. 作为测试工程师，我想看到“通过”“不通过”或“非标准但可转换”的校验状态，以便决定下一步行动。
23. 作为测试工程师，我想在安全风险、文件损坏或不可转换错误时不能转换或加入任务列表，以便危险数据不会进入平台。
24. 作为测试工程师，我想在“非标准但可转换”时看到“转为标准格式”入口和首版开发中提示，以便知道该能力尚未承诺完成。
25. 作为测试工程师，我想在校验通过后点击“加入任务列表”，以便创建可管理但尚未执行的导入型采集任务。
26. 作为测试工程师，我想在上传、校验、转换和创建请求期间看到进行中状态并禁用对应按钮，以便不会重复提交。
27. 作为测试工程师，我想让导入 ZIP 必须包含 manifest、至少一路视频和一个 IMU 文件，以便输入具备最低可执行结构。
28. 作为测试工程师，我想让 manifest 声明视频通道、帧率、分辨率、码率和时间来源，以便视频元数据能够被审查和检查。
29. 作为测试工程师，我想让每路视频提供起始原始设备时间，以便容器 PTS 能映射到设备原始时钟。
30. 作为测试工程师，我想让导入支持 1～4 路 H.264 MP4/MKV 视频，以便复用平台的多路视频检查能力。
31. 作为测试工程师，我想让平台从视频容器 PTS 获取逐帧相对时间，而不是强制旁路逐帧文件，以便减少导入负担并保持来源可追溯。
32. 作为测试工程师，我想导入至少 100Hz 的 CSV 或 JSONL 六轴 IMU，以便实际数据满足平台的最低分析密度。
33. 作为测试工程师，我想让 IMU 明确包含三轴加速度和三轴角速度，以便传感器契约完整且可检查。
34. 作为测试工程师，我想让加速度使用 m/s²、角速度使用 rad/s，并冻结坐标系、字段顺序和精度，以便不同来源数据可以一致消费。
35. 作为测试工程师，我想让导入数据可选包含设备状态、设备日志和其他附件，以便缺少非核心证据时仍能导入并收到警告。
36. 作为测试工程师，我想让实际数据不要求也不允许伪造 fault_truth.json，以便导入型运行不会冒充有故障真值的合成场景。
37. 作为测试工程师，我想让原始 ZIP 使用 SHA-256 去重，以便同一个输入不会重复加入任务列表。
38. 作为测试工程师，我想让文件名相同但哈希不同的 ZIP 被视为不同导入，以便不因名称碰撞丢失数据。
39. 作为测试工程师，我想在重复导入时跳转或关联已有任务，以便找到原始导入记录而不是得到含糊错误。
40. 作为测试工程师，我想在导入时确认我有权处理和展示这些数据，以便平台的本地展示不绕过数据使用边界。
41. 作为测试工程师，我想让上传和解压流式写入 Git 忽略的项目数据目录，以便实际数据不会进入仓库或一次性占用不可控内存。
42. 作为测试工程师，我想让平台拒绝路径穿越、加密压缩和 ZIP 炸弹风险，以便恶意或损坏的压缩包不能逃逸隔离区或耗尽资源。
43. 作为测试工程师，我想让 ZIP 最大为 2GiB、解压后最大为 10GiB、最多 100 个文件、单文件最大 5GiB 且压缩比不超过 100:1，以便资源边界是确定且可验证的。
44. 作为测试工程师，我想让临时隔离区默认保留 24 小时并支持手工移除，以便失败输入可短期复查且不会无限期占用空间。
45. 作为测试工程师，我想让校验通过的数据以原子操作进入正式数据目录，以便不会出现半入库的导入任务。
46. 作为测试工程师，我想长期只保留 ZIP 哈希、导入时间、校验器版本、最终状态、错误和警告摘要、文件清单与哈希，以便导入可追溯但不保留不必要的扫描细节。

101. 作为测试工程师，我想让超时、限流和临时服务错误最多自动重试两次，而其他错误直接保留并允许人工重试，以便成本和失败行为可预测。
102. 作为测试工程师，我想让诊断保存服务商、模型、Prompt 版本、证据包、生成时间和 Mock 状态，以便结果可以复查。
103. 作为测试工程师，我想让 AI 输出包含结构化诊断状态、现象、可能原因、证据引用、置信级别、影响范围、复测建议、缺失证据、限制和不确定性，以便诊断结论可审查。
104. 作为测试工程师，我想让无证据支持的内容只能标记为推测，以便模型不能把猜测伪装成事实。
105. 作为测试工程师，我想让证据引用必须指向诊断证据包中的稳定编号，以便诊断结论可以回溯。
106. 作为测试工程师，我想让合成型运行将诊断原因与故障真值对照，以便统计命中、漏判和无证据推测。
107. 作为测试工程师，我想让导入型运行不计算故障真值对照指标，以便评估边界符合实际数据没有预置真值的事实。
108. 作为测试工程师，我想在 AI 失败时保留运行完成状态、检查结果和原始报告，以便稍后单独人工重试诊断。
109. 作为测试工程师，我想让页面解释 AI 只做辅助判断而不生成阈值、不执行设备操作和不改变确定性事实，以便正确理解平台责任边界。
110. 作为测试工程师，我想让所有导入、生成、运行、检查、对齐、人工结果、诊断和导出错误都有明确的外部状态，以便异常、降级和失败都可定位。

## Implementation Decisions

- RC2 的正式页面信息架构固定为仪表盘、新建任务、根据导入生成、已保存任务和运行详情；设置作为顶栏入口。根据导入生成是独立标签页，实际测试 ZIP 导入流程不得隐藏在合成任务表单中。
- 合成型和导入型采集任务共享任务列表、运行记录、确定性检查、时间对齐、人工检查结果、报告、证据包和诊断运行能力，但数据来源和故障真值语义必须显式区分。
- AI 服务通过独立的服务商适配边界调用。RC2 服务商固定为硅基流动、DeepSeek 和 Kimi；每个服务商独立维护凭据、端点、推荐模型目录和自定义模型输入。不得跨服务商复用或发送凭据。
- 连接测试、模型选择、请求状态和错误信息必须带服务商与模型语义。模型名称错误不得静默回退。默认仍保留离线 Mock 模式。
- 快速模式的 IMU 采样率冻结为 100Hz；自定义模式仍允许 50、100、200、500Hz。标准模式继续按既有正式配置执行。
- 合成 IMU 固定为六轴：三轴加速度和三轴角速度。单位分别为 m/s² 和 rad/s；坐标系、字段顺序、精度、采样率和故障注入规则必须进入稳定数据契约。
- 合成和导入数据都必须保留 `raw_device_timestamp_ns` 以及相对时间。视频帧时间由容器 PTS 与每路视频的起始原始设备时间派生，并保留帧号和时间来源。
- 对齐时间是派生结果，不得回写或覆盖视频、IMU 或其他原始证据的时间字段。对齐结果至少保留参考时钟、方法、参数、对齐前指标和对齐后残差。
- 逐帧映射按每一路视频帧执行：以视频帧时间为基准，在完成时钟对齐后的 IMU 时间序列中选择时间差最小的样本。
  映射必须记录双方原始时间、相对时间和对齐时间、视频帧号、IMU 样本序号、真实时间差、容差和匹配状态；不把不同采样点宣称为完全同时。
- 逐帧映射作为独立派生产物输出，建议默认文件名为 `frame-imu-alignment.csv`。报告、独立 HTML 和证据 ZIP 必须能引用该产物；最终字段名以实现时冻结的数据契约为准，但不得删除上述语义。
- 视频配置新增码率契约，必须定义单位、合法范围、预设值以及 CBR/VBR 语义，并同步进入配置快照、生成、检查和报告。H.264、MP4/MKV、1～4 路视频边界保持不变。
- “根据导入生成”只接受单个 ZIP，不接受单文件或零散多文件。ZIP 必须包含 `manifest.json`、至少一路视频和一个 IMU 文件。
- manifest 必须声明视频通道、帧率、分辨率、码率和时间来源，并为每路视频提供 `start_raw_device_timestamp_ns`。逐帧旁路文件不是必需输入，平台从容器 PTS 获取逐帧相对时间。
- 导入 IMU 支持 CSV/JSONL，最低 100Hz，必须包含六轴数据、原始设备时间和相对时间。`aligned_timestamp_ns` 只能是平台生成的可空派生字段，不能覆盖原始字段。
- 设备状态、设备日志和其他附件是可选输入；缺少它们属于警告而不是失败。实际数据不得包含或伪造 `fault_truth.json`。
  加入后创建来源为 `imported_actual_data` 的导入型采集任务，只填写自由测试标签，不选择合成场景。
- 导入校验分为安全与结构校验、平台兼容性校验，结果固定为通过、不通过、非标准但可转换。错误禁止加入任务列表；警告允许加入并在任务和报告中持续显示。
- 非标准但可转换的首版入口只展示“该功能开发中”提示。安全风险、损坏文件和其他不可转换错误禁止转换和入库。
- 原始 ZIP 的 SHA-256 是去重主键。相同哈希不得重复加入，可关联或跳转到已有任务；名称相同但哈希不同仍视为不同导入。
- 导入数据在上传和解压期间写入项目数据目录下的隔离区，该目录必须被 Git 忽略。上传前要求用户确认具有处理和展示权限。通过校验后以原子操作移动到正式目录。
- 安全限制固定为 ZIP 最大 2GiB、解压后最大 10GiB、最多 100 个文件、单文件最大 5GiB、压缩比不超过 100:1，并拒绝路径穿越、加密压缩和 ZIP 炸弹风险。处理应采用流式边界检查。
- 原始 ZIP 与解压文件不可变保存。长期导入凭证只保留 ZIP 哈希、导入时间、校验器版本、最终状态、错误和警告摘要、文件清单及哈希；详细临时扫描日志不长期保存。重新校验可以更新当前结果，但不改变首次导入凭证和原始哈希。
- 临时隔离区默认保留 24 小时并支持手工移除。任务加入列表后不自动运行；测试工程师先配置参考时钟、判定模式和阈值，再手工执行。导入型运行自动执行所有适用的确定性检查，缺少可选证据的检查状态为未执行。
- 合成型和导入型任务采用统一生命周期：从未执行的任务可删除；已有运行记录的任务只能归档，不能删除、级联删除或改变原始证据。归档不影响运行、报告、诊断和下载能力。
- 已保存任务提供筛选和每页 10 条的分页读模型，并显示数据来源、执行状态、是否已有运行、任务名称和归档状态。运行详情提供任务名称、任务内执行序号、内部运行 ID、队列位置和阶段状态。
- 原始视频提供独立下载。证据 ZIP 默认排除原始视频，只允许显式包含受限小样；ZIP 记录导出时间并按导出时的当前运行、人工结果和诊断状态生成。
- 面向 Excel 的 CSV 采用 UTF-8 BOM。人工结果导入和导出使用同一契约；如存在用途不同的文件，必须提供明确命名和独立模板，避免导出结果直接导入时列不兼容。
- AI 诊断请求具有请求中、成功、失败和可重试状态；请求中禁用重复提交，刷新不自动重新提交。接受明确允许的结构化包装，最终结果仍须通过 Schema 和证据引用校验。
- 内部异常映射为稳定、用户可读的错误码和摘要，详细堆栈只写入受控日志。诊断运行独立保存，不改变测试执行状态。只有超时、限流和临时服务错误自动重试，最多两次；其他错误保留并允许人工重试。
- 诊断输出仍须包含结构化状态、现象、原因、证据引用、置信级别、影响范围、复测建议、缺失证据、限制和不确定性。AI 不得生成阈值、控制设备或覆盖检测结果、人工结果、故障真值和原始时间。
- 重新执行始终创建新的运行记录并复制配置快照；前端切换运行或重新执行时清空并重新加载当前运行的诊断状态，旧诊断只归属于旧诊断运行。
- 以上决定继续遵守洁净重写、保留对齐前后结果、区分正式规格/工程目标/版本基线、AI 不进入测试关键路径和结构化可评估诊断等既有 ADR。若未来需要改变这些边界，必须另行形成 ADR，不在 RC2 实现中隐式覆盖。

## Testing Decisions

- 主测试 seam 使用现有的 FastAPI TestClient 公开 HTTP API 集成测试。测试只断言测试工程师可观察的响应、状态迁移、数据契约、文件内容、下载边界和持久化结果，不绑定内部函数调用或数据库实现细节。
- 前端沿用现有 React Testing Library 的 App、页面和组件 seam，验证页面/标签切换、字段可见性、请求中禁用、成功/失败提示、重复提交防护、运行切换和导出入口等用户可观察行为。
- 后端测试应覆盖：三服务商配置隔离与连接测试、模型目录和非法模型错误、密钥不落盘、AI 降级与重试、结构化包装兼容和真实响应回放；快速模式 100Hz 与自定义 50Hz；六轴 IMU 字段、单位、坐标和重复性。
- 后端测试应覆盖：原始设备时间与相对时间同时保留、对齐结果不覆盖原始值、逐视频帧最近邻 IMU 选择、真实时间差、容差和未匹配状态，以及映射文件被报告和证据包引用。
- 后端测试应覆盖：视频码率边界和检查、CSV/JSONL 导入、manifest 必填字段、缺少可选证据的警告、禁止 fault_truth、ZIP 哈希去重、同名异哈希、重新校验凭证稳定性和导入型运行语义。
- 后端测试应覆盖：单 ZIP 输入、流式大小限制、文件数量、压缩比、单文件大小、路径穿越、加密压缩、ZIP 炸弹、隔离区保留、原子入库、权限确认和 Git 忽略目录约束。安全拒绝不得留下可下载的半成品。
- 后端测试应覆盖：合成型和导入型任务的删除/归档状态机、已有运行禁止删除、原始证据不被级联删除、分页和筛选、队列位置、运行详情读模型、取消、重启中断、复测新记录和诊断归属。
- 后端测试应覆盖：原始视频独立下载、证据 ZIP 默认排除视频、显式受限小样、导出时间和当前状态提示、UTF-8 BOM、人工结果无损回导和缺少可选证据时的未执行状态。
- 前端测试应覆盖：导入页面四个按钮的可用性状态、校验结果分层展示、重复请求禁用、失败降级提示、任务列表归档/删除入口、分页/筛选、运行详情切换、原始视频与证据 ZIP 下载入口，以及三服务商选择和模型错误反馈。
- 现有测试先例包括任务创建与配置 API、运行管理 API、固定偏移和线性漂移 API、IMU 运行 API、人工结果 API、报告与证据 ZIP API、
  硅基流动契约测试、Mock 诊断测试，以及 App、任务表单和运行详情组件测试。RC2 优先扩展这些既有 seam，不新建低层测试 seam。
- 确定性检查应先于主观 UI 复核：先验证 Schema、状态机、哈希、文件清单、时间映射、大小边界和安全拒绝等可重复断言，再对页面信息架构和窄/宽屏布局做人工视觉验收。
- 测试不得读取、复制或依赖原公司的代码、数据、Prompt、接口、文档或资产；实际测试 ZIP 仅作为用户本地输入契约验证对象，不进入仓库、spec 或测试固件。
- 测试工程师使用手册必须是独立、可从 README 进入的文档，不能只有启动命令或功能概述。手册至少要逐项解释快速、标准、自定义模式，
  所有参数的取值和效果，六轴 IMU 采样率差异，内置场景注入和预期检查，固定偏移/线性漂移，三种判定模式，manifest 字段，
  导入状态、失败/警告、去重、归档和证据导出。文档完整性必须有文件检查或人工验收证据。

## Out of Scope

- 不实现真实设备连接、设备控制、音频、蓝牙、真实 MCAP 或复杂非线性时间扭曲。
- 不在 RC2 中实现“转为标准格式”；只实现入口、状态和“该功能开发中”提示，并记录未来不得编造绝对时间的约束。
- 不接受单文件、零散多文件或没有 manifest 的实际数据导入。
- 不把用户实际数据、原始 ZIP、解压文件、密钥或公司资产提交到仓库，也不把洁净重写项目改造成原公司产品复刻。
- 不为导入型数据伪造故障真值，不计算导入型运行的真值对照诊断指标。
- 不让 AI 生成阈值、执行确定性检查、控制设备、修改原始证据、修改人工结果或改变运行状态。
- 不在本 spec 中冻结容易过时的具体代码文件路径、函数实现或框架重构方案。
- 不建立多人账户、管理员权限、审批流、云端数据托管或团队协作权限模型。
- 不拆分 RC2 implementation tickets；tickets 将在本 spec 单独确认发布后另行处理。
- 不修改 v0.1.0-rc.1 的 `docs/test-case-input/` 文件，也不复用其中的原公司代码、数据、Prompt、接口或文档内容。

## Further Notes

- 本 spec 以 `docs/rc2-feedback-triage.md` 已确认的 34 条范围和第 7 节七项确认结论为准，不重新访谈业务需求。
- 第 34 条导入设计中的 ZIP、manifest、校验状态机、安全边界、去重、数据不可变和生命周期决定在 RC2 中视为已确认契约，而不是可选建议。
- 现有 ADR-0003 将硅基流动定义为默认服务；RC2 扩展 DeepSeek 和 Kimi，但保留独立适配层、Mock 模式和 AI 不进入测试关键路径的架构决策。
- 现有 ADR-0004 要求保留对齐前后结果；RC2 进一步明确原始设备时间、相对时间、对齐时间和逐帧映射必须并存。
- 导入型任务共享平台的运行和报告能力，但导入本身只创建任务，不自动执行；用户必须明确发起运行。
- 证据 ZIP 是按当前状态生成的导出物，不是自动变化的持久化快照。用户改变人工结果或诊断后，应重新导出以获得最新内容。
- 任务生命周期和原始数据不可变优先于便捷删除；任何未来的清理能力都必须保留运行记录和最小导入凭证。
- 本条目使用本地 Markdown tracker 的 `ready-for-agent` 状态，不发布到 GitHub Issues。本会话不提交或推送 Git。
