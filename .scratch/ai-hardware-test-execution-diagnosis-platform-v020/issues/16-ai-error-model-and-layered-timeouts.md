# 16 — 模型调用错误分类与分层超时

**What to build:** 把现在的单一 30 秒超时和粗粒度错误类型换成可配置的分层超时与结构化错误模型。用户必须能看出是目录查询、连接测试还是业务请求失败，失败属于哪一类，能否重试，下一步做什么。详细规则见 [AI 接入护栏](../../../docs/ai-integration-guardrails.md)。

**Blocked by:** 15 — AI 配置快照与验证状态失效

**Status:** ready-for-agent

**当前前端 Demo 对应页面：** 首页连接测试结果、报告 AI 区域的失败提示。

- [x] 模型目录查询、连接测试和业务请求使用各自可配置的超时，错误信息指明是哪一层超时。
- [x] 统一错误结构：`stage`、`kind`、`retryable`、`user_message`、`action`、脱敏后的 `diagnostic`。
- [x] `kind` 至少区分 DNS、TLS、代理、连接失败、鉴权、权限、模型 ID 无效、限流、服务商 5xx、超时、输出截断、响应不可解析和 Schema 校验失败。
- [x] 只有瞬时错误自动重试：最多一次、退避 1 秒、退避过程可取消、计入调用上限。
- [x] 鉴权失败、权限不足、模型 ID 无效、确定性 4xx 和 Schema 业务字段缺失一律不重试。
- [x] 错误与诊断持久化，响应、界面提示和数据库中都不得出现密钥、Authorization 头或完整请求体。
- [x] 连接测试只做最小请求验证，不证明业务能力；界面文案不得把连接测试通过写成"模型可用"或"AI 可用"。
- [x] 每次模型请求记录 provider、模型、Endpoint 主机名、网络方式、Prompt 版本、阶段、耗时和 Token 用量（服务商提供时），且不含密钥。
- [x] fake provider 覆盖上述每种错误类型，并断言输出中不泄露密钥。

## 边界

- 本项目当前是同步请求，不引入流式响应；若后续改流式，需要另加"首个响应等待"和"流式停顿"两档超时。
- 超时默认值（目录与连接测试 20 秒、业务请求 600 秒）为起始值，随服务商和模型能力调整，不写死在代码里。
- 不改动 ADR 0006 关于 AI 不进入测试执行关键路径的结论。

## 2026-10-30 完成记录

- 模型目录、连接测试和业务请求分别使用可配置超时（`AI_CATALOG_TIMEOUT_SECONDS`、`AI_CONNECTION_TIMEOUT_SECONDS`、`AI_BUSINESS_TIMEOUT_SECONDS`），超时消息带阶段和秒数。
- 引入结构化错误：stage、kind、retryable、user_message、action、脱敏 diagnostic，以及 provider/model/Endpoint 主机、网络方式、Prompt 版本、耗时、尝试次数、HTTP 状态、finish_reason、响应长度和 Token 用量。
- 错误分类覆盖 DNS、TLS、代理、连接、鉴权、权限、模型 ID、限流、5xx、超时、输出截断、响应不可解析和 Schema 校验；鉴权、权限、模型、确定性 4xx、Schema 失败不重试。
- 重试改为最多一次、退避 1 秒且可取消，计入单次运行调用上限；请求日志写入 `ai_request_logs`，诊断/报告分析/验证记录保存结构化错误。
- 首页连接失败展示“下一步”建议，报告 AI 区域失败展示 action；界面明确连接测试只验证最小请求，不证明业务能力。
- 证据：`backend/tests/test_ai_error_model.py`（13 项：7 种 HTTP 错误、网络分类、分层超时、重试/取消、请求日志、验证错误持久化、截断）、迁移测试更新到 schema 30、前端原型与报告分析断言更新。后端 187 通过，前端 151 通过 / 3 跳过，`tsc -b`、`vite build`、Prettier、Ruff 与仓库安全检查均通过。
- 剩余：错误分类依赖 HTTP 状态和异常文本，部分 4xx 无法区分具体原因；流式首响应/停顿超时未实现（当前同步请求）；截断后的修复与分批由 17/18 接入；请求日志暂无查询页面。
