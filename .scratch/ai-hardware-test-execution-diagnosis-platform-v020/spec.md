# v0.2.0 智能硬件测试执行与诊断平台规格

Status: ready-for-agent
Version: v0.2.0

## Problem Statement

测试工程师需要把 Beta 产品版本的原始测试用例整理为可执行的自动化测试用例，选择平台中已经生成或校验过的测试数据，配置多个测试组，执行数据驱动的自动化检查，并把自动化结果与人工测试结果合并为按模块分析的最终报告。

当前 v0.1.0 主要提供测试数据生成、导入、校验和运行记录。它还没有项目/产品版本、原始用例与自动化用例、测试组、自动化执行快照、独立人工结果和 v0.2.0 最终报告之间的完整关系。v0.2.0 需要建立这条完整流程，同时保持 v0.1.0 数据任务可以作为测试数据输入来源。

平台还需要让 AI 参与原始用例到自动化用例的转换。用户必须能够查看、编辑、删除、新增和校验生成结果；AI 失败时需要通过表格视觉状态和简短备注表达，不得把用户重新变成手工编写全部自动化用例的人。

## Solution

建设一条以产品版本为边界的测试工作流：

```text
项目版本
→ 需求/测试用例资料导入
→ 原始测试用例表
→ AI 辅助生成自动化用例表
→ 已校验测试数据包
→ 自动化测试设置
→ 数据驱动模拟执行
→ 自动化执行记录快照
→ 独立人工测试结果
→ 按模块生成最终报告
```

项目是长期工作容器，产品版本用于区分 Beta 产品版本。测试组属于项目版本，保存本次测试范围和用例/数据包关系。平台级数据包可以被多个测试组和多个自动化用例使用。

最终报告合并用户选择的同一测试组、同一产品版本下的一条自动化执行记录和一条或多条人工测试记录。报告按原始用例的“模块”字段组织，每个模块开头突出当前结论，并提供自动化结果、人工结果、必要支撑数据以及 AI 风险和补充验证建议。阶段推进内容只是平台建议，公司根据实际情况决定是否进入下一阶段。

## User Stories

1. 作为测试工程师，我想创建项目和产品版本，以便按产品长期管理测试资产。
2. 作为测试工程师，我想在项目详情中查看产品版本和趋势，以便了解历史测试变化。
3. 作为测试工程师，我想在首页配置 AI 模型或暂不配置，以便按当前环境选择是否使用 AI。
4. 作为测试工程师，我想导入 Beta 产品需求或测试用例资料，以便把已有测试内容带入平台。
5. 作为测试工程师，我想在导入前核对字段映射，以便确认平台识别了我的常用字段。
6. 作为测试工程师，我想选择是否导入历史测试结果、测试记录、测试前备注、计划执行时间和附件，以便控制导入范围。
7. 作为测试工程师，我想保留原始测试用例表，以便自动化转换不会覆盖源数据。
8. 作为测试工程师，我想按模块、测试项、优先级和软件版本筛选原始用例，以便集中处理目标范围。
9. 作为测试工程师，我想全选、反选和勾选原始用例，以便形成待加入测试组的清单。
10. 作为测试工程师，我想关闭网站后仍保留勾选清单，以便下次继续工作。
11. 作为测试工程师，我想让 AI 根据整张原始用例表生成自动化用例表，以便减少手工改写工作。
12. 作为测试工程师，我想在没有 AI 时使用规则转换得到低可信度候选，以便仍能开始整理自动化用例。
13. 作为测试工程师，我想看到转换失败的行颜色和简短原因，以便快速定位需要处理的内容。
14. 作为测试工程师，我想让自动化用例保留一个可点击的来源用例编号，以便回看原始用例。
15. 作为测试工程师，我想编辑自动化用例的标题、输入、操作步骤和预期结果，以便适配实际可执行方式。
16. 作为测试工程师，我想新增自动化用例并填写来源用例编号，以便补充原始表中遗漏的自动化内容。
17. 作为测试工程师，我想删除不属于自动化范围的用例，以便保持自动化表简洁。
18. 作为测试工程师，我想在独立的 AI 反馈列填写命令行或步骤修改意见，以便与后台 AI 迭代转换结果。
19. 作为测试工程师，我想一次提交一条或多条已修改用例，以便按自己的工作节奏提交反馈。
20. 作为测试工程师，我想在反馈提交给 AI 后清空反馈输入内容，以便下一次校验使用新的反馈。
21. 作为测试工程师，我想校验当前自动化用例表，以便确认编号、来源和内容可以进入后续流程。
22. 作为测试工程师，我想在修改后看到“未校验”状态，以便知道不能直接执行。
23. 作为测试工程师，我想查看自动化转换记录，以便了解原始内容、初始转换和用户修改过程。
24. 作为测试工程师，我想执行 v0.1.0 的数据生成或导入任务，以便获得测试输入数据。
25. 作为测试工程师，我想查看数据包是否符合平台标准格式，以便避免把不合规输入带入测试组。
26. 作为测试工程师，我想查看数据包中的文件、通道、时间戳和完整性，以便了解实际测试输入。
27. 作为测试工程师，我想区分正常数据和故障数据，以便验证系统能否发现故障场景。
28. 作为测试工程师，我想筛选生成数据、导入数据、正常数据和指定故障数据，以便快速找到目标数据包。
29. 作为测试工程师，我想看到数据包编号、来源任务和更新提示，以便判断当前使用的输入是否发生变化。
30. 作为测试工程师，我想选择已有且已校验的数据包，以便测试组不会直接使用未经验证的文件。
31. 作为测试工程师，我想把一个数据包批量关联到多条自动化用例，以便快速配置测试范围。
32. 作为测试工程师，我想在测试组用例表的“数据包”列逐条切换或取消关联，以便精确调整单条用例。

35. 作为测试工程师，我想创建多个自动化测试设置，以便分别验证基础回归、故障场景和专项功能。

46. 作为测试工程师，我想让故障数据被正确检测时用例显示失败，以便报告真实反映预期检查未通过。
47. 作为测试工程师，我想在独立页面录入人工用例结果，以便人工测试不受自动化执行速度影响。

54. 作为测试工程师，我想在只有一类记录时仍生成报告，以便不因缺少另一类结果而失去当前事实。
55. 作为测试工程师，我想下载 HTML 和纯文字报告，以便分别用于查看、传递和存档。

57. 作为测试工程师，我想在报告中按模块看到当前结论和支撑数据，以便知道每个模块的实际风险。
58. 作为测试工程师，我想让 AI 在报告后给出风险、补充验证、回归测试和下一版本必测项建议，以便安排后续工作。
59. 作为测试工程师，我想让 AI 失败时仍看到事实报告，以便模型不可用不影响结果交付。
60. 作为测试工程师，我想在项目详情中筛选趋势和主动比较版本或报告，以便观察模块结果变化。
61. 作为测试工程师，我想让 GitHub Actions 验证平台自身的固定样例，以便确认 v0.2.0 代码没有破坏既有流程。
62. 作为平台维护者，我想为需求点拆解、测试用例生成、自动化用例转换和报告分析保留统一接口，以便后续接入或替换 Skill 时不重构业务流程。
63. 作为平台维护者，我想暂时关闭需求点拆解和测试用例生成能力，以便 v0.2.0 不提前实现 v0.3.0 的产品能力。
64. 作为平台维护者，我想替换自动化用例转换或报告分析的具体实现，以便在 Skill、模型服务和规则实现之间切换。

## Implementation Decisions

- 产品领域关系为“项目 → 产品版本 → 用例资产、测试数据资产、测试组、测试记录和最终报告”。
- 原始测试用例和自动化测试用例分开保存。自动化转换不得覆盖原始内容。
- 用户常用字段保留为：用例编号、测试用例标题、优先级、预置条件、输入、操作步骤、预期结果、测试类型、模块、测试项、测试结果、测试记录、测试前备注信息、计划执行时间、附件、软件版本。`输入`允许为空。
- 自动化用例使用系统生成的唯一编号且不可修改；来源用例编号只保留一个可点击字段，用于回到原始用例。
- 自动化用例表是一张可编辑表。AI 反馈在独立列或行展开区域呈现，不与标题混在同一列；提交按钮一次处理所有有修改或有反馈的行。
- 用户修改、新增或删除自动化用例后，相关内容标记为未校验。校验通过前不能加入测试组或执行。
- AI 转换失败通过明显行背景色和简短备注说明，避免增加大量低价值分析字段。
- 无 AI 时可以使用规则转换，但必须标记低可信度并要求人工审核；规则来源应可持续积累和维护。
- v0.1.0 的采集任务表示数据生成、导入和检查任务。它可以不在每次自动化测试前重新运行，已有合规数据包可以直接作为输入。
- 测试组数据包只能从平台内已经生成并校验或导入并校验的数据包中选择。测试组详情中的用例表最后一列直接显示和调整数据包。
- 数据包与自动化用例是多对多关系。取消一条关联不影响其他用例或测试组。
- 数据源任务产生新结果时提示输入源已更新，默认推荐最新结果，但不自动替换已有关系；需要复现时可以继续使用旧数据包。
- 测试组创建只填写基本信息，完整用例、数据包和执行设置在详情页管理。测试组支持创建、编辑、隐藏、恢复显示和删除。
- 执行模式在点击“执行自动化测试”时选择。v0.2.0 只提供数据驱动模拟；模拟设备状态机、ADB/HTTP/Shell 执行属于 v0.4.0；真实设备连接属于更后版本。
- 执行前检查失败只允许在准备流程中重新检查，不创建正式自动化执行记录。真正开始执行后创建带编号、时间和完整配置快照的不可覆盖执行记录。
- 执行开始后的再次执行、失败、取消或中断都保留新的执行记录，不覆盖旧记录。
- “测试结果完成”表示计划项目已经完成尝试，不要求所有结果通过。失败、阻塞和未执行继续作为事实结果显示。
- 人工测试结果使用独立录入页面，但保留项目侧栏和当前项目/版本/测试组上下文。人工结果可分批保存、修改、删除和重复使用。
- 最终报告页面只选择记录、生成、查看、下载和清理附件，不负责录入人工结果。
- 报告只合并同一测试组、同一产品版本的一条自动化记录和一条或多条人工记录。缺少一类记录时显示未执行或没有对应记录，不阻塞事实报告生成。
- 报告固定顺序为：测试基本信息、阶段推进评估、AI 分析、测试范围总览、按模块详细结果、跨模块问题/补充验证/回归建议。
- 阶段推进评估是平台建议，不是强制准入开关，也不要求测试工程师点击批准。
- 每个模块开头突出显示当前结论，结论必须有实际结果和支撑数据，不编造统计值。
- AI 只产生转换建议、风险和后续建议，不自动修改测试资产或事实结果。AI 分析失败时事实报告仍可查看并可单独重试。
- 在线报告重新生成会覆盖当前在线报告；用户已经下载的 HTML 和纯文字文件不受影响。删除在线报告不删除底层测试记录和数据包。
- 报告正文只放必要支撑数据。详细原始日志、证据包、哈希码和未影响判断的过程数据不默认生成。
- 人工附件在报告使用后可从报告页面清理，报告保留文字结果、附件名称和已清理状态。
- 趋势图只出现在项目详情，统计已经生成的最终报告；首页不显示趋势看板。版本对比由用户主动选择两个产品版本或两份最终报告。
- GitHub Actions 只验证平台自身的固定样例、前后端构建和回归测试，不连接客户真实设备、不执行客户产品测试、不根据客户测试失败阻断仓库。
- 当前 Web Demo 是界面和状态流验证材料，不代表后端领域模型、接口和持久化已经完成。
- 四类 AI 能力必须通过平台内部接口访问，业务模块不能直接依赖某一个 Skill 的目录或文件格式：`RequirementPointAnalysisService`、`TestCaseGenerationService`、`AutomationCaseConversionService` 和 `ReportAnalysisService`。
- v0.2.0 为四类接口建立可替换实现。需求点拆解和测试用例生成暂时使用关闭实现；自动化用例转换至少提供规则实现，并允许接入 AI/Skill 实现；报告分析允许接入 AI/Skill 实现，并在不可用时降级。
- Skill 适配器、模型服务适配器和规则实现均属于接口下游实现。前端只调用平台业务接口，不直接调用 Codex Skill。
- Skill 本身不会成为产品运行时的强制依赖。产品运行时是否产生模型 API 消耗，由实际启用的 AI/Skill 适配器和模型服务决定。

## Testing Decisions

- 测试以用户可观察行为为主，验证页面状态、领域关系、结果表达和删除/过期影响，不绑定具体组件实现。
- 首先建立确定性校验：字段映射、自动化编号、来源编号、未校验状态、数据包格式、数据包关联、执行前检查、执行快照、记录范围和报告输入限制。
- 项目/版本和用例资产测试覆盖创建、导入、筛选、勾选持久化、自动化转换、编辑、反馈提交、校验和来源跳转。
- 数据资产测试覆盖 v0.1.0 任务结果选择、格式检查、正常/故障识别、生成/导入筛选、更新提示、多对多关联和单条数据包调整。
- 测试组和执行测试覆盖多个测试组、详情编辑、数据包限制、执行模式、执行前失败重试、执行编号/时间、不可覆盖快照和再次执行新记录。
- 人工结果测试覆盖按测试组逐条录入、分批保存、恢复编辑、缺失显示未执行、附件使用和清理。
- 报告测试覆盖自动化与人工结果合并、单类结果报告、失败不阻塞报告、按模块结论、支撑数据、AI 失败降级、HTML/纯文字下载、在线报告过期/覆盖/删除和趋势数据来源。
- 前端 Demo 继续使用当前项目的 TypeScript 检查和 Vite 构建作为基本验证；新增业务功能后补充 API、数据库和端到端测试。
- GitHub Actions 的 v0.2.0 验收样例必须使用固定数据和固定预期结果，能够验证平台流程，不应把客户设备执行结果混入 CI。
- 对 AI 转换和报告 AI 使用确定性样例、结构化输出校验和失败降级测试；AI 输出只能影响建议区域，不能改变事实结果。
- 四类 AI 能力接口测试覆盖启用、关闭、不可用、超时和无有效输出状态。关闭的前两个接口必须明确返回未启用状态，不得伪造已完成的需求点或测试用例。
- 自动化用例转换接口测试覆盖规则实现和可选 AI/Skill 实现的统一输出结构；报告分析接口测试覆盖事实报告不依赖 AI、AI 失败不阻塞报告生成。

## Out of Scope

- 真实被测设备连接、设备发现、权限管理和现场环境检查。
- 模拟设备状态机以及 ADB、HTTP、Shell 等设备能力的真实模拟执行。
- 深度需求结构化、需求到用例的完整追踪、自动化范围推荐和自动生成回归计划。
- AI 自动修改用户测试组、用例、数据包或事实结果。
- v0.2.0 不实现需求点拆解和需求点到测试用例的完整产品流程，只建立接口、关闭实现和后续接入位置。
- 强制质量门禁、强制准入批准和用报告结果替公司决定是否推进下一阶段。
- GitHub Actions 作为客户产品测试执行器、设备云环境或正式质量门禁。
- 默认生成证据包、哈希码和大量原始日志。
- 用归档替代删除；用户可以在看到影响范围后删除测试组、执行记录、报告、数据包和转换记录。
- 把 v0.1.0 的数据任务运行记录直接当作 v0.2.0 自动化执行记录。
