# AI 智能硬件测试执行与诊断平台

Status: ready-for-agent

## Problem Statement

面向 Python 自动化测试、兼顾智能硬件或嵌入式测试岗位的测试工程师，需要一套能够独立运行、可演示且有验证证据的作品项目。在没有真实设备、没有公司数据且不能复用原公司资产的前提下，测试工程师仍需稳定复现多路视频、IMU、设备状态和日志中的典型数据质量问题，执行可重复的确定性检查，并清楚区分原始时间差异、时间对齐效果和验收结论。

现有设计还需要解决三类信任问题：自动化事实与 AI 推测不能混淆；人工结果与自动化结果不能互相覆盖；模型服务不可用时不能阻断测试执行和原始报告。所有演示结果都必须来自可复现的合成数据、明确的故障真值和可核验的报告证据，而不是不可验证的功能描述。

## Solution

建设一个本机运行、单测试工程师使用的“智能硬件测试执行与诊断平台”。平台从采集任务生成不可覆盖的运行记录，使用固定随机种子生成短视频、IMU、设备状态和日志，并用虚拟时间模拟长稳趋势。六个内置场景携带预先定义的故障真值和预期检测结果。

平台先执行不依赖 AI 的确定性检查，再对原始时间戳进行固定偏移或线性漂移校正，同时保留对齐前指标、校正参数和对齐残差。测试工程师可按正式规格、工程目标或版本基线评价结果，也可独立录入人工检查结果。

完成确定性流程后，平台从失败指标、异常窗口日志、资源指标、关键帧、IMU 摘要和人工结果中构建限量且带稳定引用编号的诊断证据包。硅基流动适配器或固定 Mock 返回结构化诊断，系统校验证据引用并对照故障真值评估诊断效果。模型失败只影响诊断运行，不改变测试执行状态。

最终平台提供应用内报告、可独立打开的 HTML 报告、带清单和哈希的 ZIP 证据包，以及用于验证项目自身质量的 Allure 和持续集成产物。

## Implementation Decisions

- 项目必须采用洁净重写，只使用个人掌握的通用经验、虚构设备、公开格式和确定性合成数据；不得复制或复用原公司的代码、数据、Prompt、接口、文档、界面、名称、截图或未公开信息。
- 首版采用前后端分离架构：Python、FastAPI 和 Pytest 构成后端及自动化测试能力，React 与 TypeScript 构成前端，SQLite 负责本地持久化，pnpm 负责前端依赖管理。
- FFmpeg 和 ffprobe 负责 H.264 视频生成与检查；Allure 展示项目自身测试结果；GitHub Actions 执行持续集成，默认不调用真实模型。
- 首版是单用户、本机应用，不建设账户、权限、审批或多人协作。执行器同时只运行一个测试任务，其他任务排队。
- 采集任务保存可重复使用的场景和参数；每次执行创建不可覆盖的运行记录，并保存配置快照、阶段状态、证据、检测结果和报告。
- 测试执行状态包括草稿、排队、生成数据、执行检查、汇总结果、已完成、执行失败、已取消和异常中断。取消必须安全，应用重启必须识别未完成运行。
- 数据生成器支持 1～4 路视频、一路 IMU、设备状态和日志。短数据真实生成，长稳趋势使用虚拟时间；所有产物必须标记来源。
- 数据配置边界、容器、编码、分辨率、帧率、IMU 格式和采样率遵循已确认规格。非法输入和可能造成过大文件的请求必须在执行前拒绝。
- 六个内置场景必须有固定随机种子、故障真值和预期检测结果。故障真值在生成前确定，不得由检测结果或 AI 反推。
- 检查器以统一结果 Schema 输出视频、IMU、资源、日志和文件检查结果。检测结果只来自确定性规则，不依赖 AI。
- 原始时间戳允许固定偏移、抖动、漂移和不同起点。默认以第 1 路相机为参考时钟，同时允许选择其他通道。
- 时间对齐首版只实现固定偏移校正和基于多个共同事件的线性漂移校正，不实现复杂非线性时间扭曲。
- 视频时间码或跑马灯事件与 IMU 冲击峰值构成跨模态锚点。系统自动识别锚点并允许测试工程师查看、调整。
- 原始时间戳和对齐前指标不可被覆盖。对齐方法、参数、对齐后最大值、平均值、P95 和趋势作为独立结果保存。
- 时间戳对齐和画面内容同步是两项独立评价，时间接近不能替代画面内容同步检查。
- 判定依据按正式规格、工程目标、版本基线区分。只有正式规格可产生验收合格性结论；工程目标不构成产品承诺；版本基线只展示分布与趋势。
- 阈值来源进入报告，AI 不得创建、补充或修改阈值。
- 人工检查结果与检测结果独立保存，并在报告层统一汇总。人工结果支持标准状态、实际结果、备注、执行时间、小型附件及统一模板的 CSV/Excel 导入。
- AI 诊断不进入测试执行关键路径。生成、检查、汇总和原始报告在模型不可用时仍须完成。
- 模型调用通过独立适配层完成，硅基流动是默认服务商，并提供固定、可重复的 Mock 模式。
- 诊断证据包只包含与诊断相关的限量上下文，每条证据具有稳定引用编号，并同时受体积和 Token 上限约束。
- AI 诊断必须返回结构化 JSON，包含诊断状态、异常现象、可能原因、证据引用、置信级别、影响范围、复测建议、缺失证据、限制和不确定性。
- 诊断输出必须通过 Schema 和证据引用校验。无证据内容只能标记为推测；展示文本只能从结构化结果渲染。
- 诊断运行独立于运行记录，重新诊断创建新记录并保存模型、Prompt 版本、证据包摘要、生成时间、Mock 状态、输出和错误。
- 模型错误按类型处理：只对超时、限流和临时服务错误最多自动重试两次；其他错误直接保存并允许人工重试。
- AI 效果评估对照故障真值分别统计命中、漏判和无证据推测；结构有效性与诊断效果分开评价。
- 应用包含仪表盘、新建任务、运行详情、分析报告和设置五个核心页面。
- 报告包括应用内交互报告、独立 HTML 和 ZIP 证据包。ZIP 包含结构化数据、人工结果、日志、关键帧或小样、文件清单、哈希和报告，默认排除原始视频。
- API Key 默认从后端环境变量读取；前端临时输入只保存在当前会话内存。SQLite、日志、报告和证据包不得保存 Key，后端只返回是否已配置。
- 仓库只提供环境变量示例，日志必须过滤认证头和敏感字段，持续集成与发布前必须检查公司资产和敏感信息。
- 项目维护遵循证据驱动原则：课程映射只使用已规划、开发中、已实现、已验证四种状态；没有重复验证证据的功能不得标记为已验证；面试案例中的量化数据不得虚构。

## Testing Decisions

- 好测试只验证外部可观察行为，不依赖内部函数调用顺序、私有实现或数据库表细节。测试必须能够区分代码错误、环境错误、依赖错误和沙箱权限错误。
- 唯一主测试 seam 是公开 API 驱动的完整运行记录生命周期：创建采集任务、生成新运行记录、等待状态迁移、读取检测与对齐结果、触发或跳过诊断、获取报告和证据包。
- 主 seam 必须覆盖正常场景和五个故障场景，并验证正常场景不误报、故障场景命中预期检测、重新执行不覆盖历史、取消与异常中断状态正确。
- 主 seam 必须覆盖三种判定模式，验证正式规格可给出合格性结论、工程目标标明非产品承诺、摸底分析不产生合格性结论。
- 主 seam 必须覆盖模型成功、Mock、模型不可用和可重试错误，验证诊断运行与测试执行状态相互独立。
- 主 seam 必须验证 HTML 可独立打开、ZIP 清单与哈希一致、默认不包含原始视频且任何产物不包含 API Key。
- React 页面只对五个核心页面的关键用户流程和公开 API 契约做必要测试，不在 UI 层重复检查生成器、检查器或状态机内部逻辑。
- 确定性生成器使用固定随机种子的纯函数或产物契约测试，验证重复生成的哈希或等价指标、参数边界、来源标记和故障真值。
- 检查器使用统一结果 Schema 的参数化契约测试，覆盖视频、IMU、资源、日志、文件检查以及检测结果与故障真值对照。
- 时间分析使用带已知偏移和漂移参数的数据测试，验证估计参数、对齐残差、原始证据保留，以及时间戳与画面内容同步的独立结果。
- AI 适配层使用契约测试验证结构化输出、证据引用、Token 上限、错误分类、最多两次重试和固定 Mock，不在 CI 中依赖真实模型。
- 状态迁移使用可控执行器或 API 集成测试验证合法迁移、安全取消、重启后的异常中断识别，以及测试执行状态与诊断状态独立。
- 当前是全新洁净重写，代码库没有既有测试先例；首批测试以本 spec 的公开 API 主 seam 和统一 Schema 作为后续 prior art。
- Allure 用于呈现项目自身测试结果，GitHub Actions 默认执行 Mock 模式的后端、前端、契约和主流程测试。

## Out of Scope

- 任何原公司代码、数据、Prompt、接口、协议、文档、界面、截图、名称或未公开产品信息。
- 首版接入真实硬件设备，以及真实设备控制、刷机、串口、蓝牙或音频采集。
- 真实 MCAP 支持和复杂非线性时间扭曲。
- 多人账户、角色权限、审批流程、团队协作和复杂用例管理。
- AI 控制设备、修改原始事实、决定确定性检查结果或自行生成验收阈值。
- 原始视频默认打入 ZIP 证据包。
- 支付业务练习、复杂 UI 滑块算法、JMeter、Jenkins、unittest 和 HTMLTestRunner。
- 测试设计与治理平台及其需求评审、风险分析、用例生成和覆盖率治理能力。
- 音频、蓝牙、真实设备适配、AI 接口专项、日志异常专项、回归选择和 Jenkins 对照实验等可选扩展。
- 本 spec 不拆分实施 tickets，也不代表任何功能已经实现或验证。

## Further Notes

- 本 spec 综合现有领域术语、规格、分阶段开发计划、七项 ADR、课程覆盖映射、面试案例和工程日志，保留所有已确认设计，不重新解释或覆盖 ADR。
- 开发顺序仍遵循“先工程骨架和确定性执行，再报告，最后 AI 诊断与效果评估”，每一阶段都应产生可观察证据。
- 正式规格、工程目标和版本基线必须始终使用领域词汇中的准确含义，避免把工程摸底结果包装为正式验收承诺。
- 诊断结论是有证据和不确定性约束的辅助判断，不是检测结果、故障真值或根因证明。
- 后续实施完成时，应同步更新课程覆盖、工程日志和面试案例；只有真实运行数据可以进入量化结果和 STAR 表达。
