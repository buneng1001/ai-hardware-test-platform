# V0.3.0｜08 智能回归测试建议详细 Spec

> 状态：核心业务方向、报告输入边界、主报告/辅助报告规则、辅助报告标签式多选及搜索/筛选/空状态、四段式回归分析说明、连续回归用例表及主表/行详情字段、逐行勾选与批量应用、来源依据精简展示、目标资产应用规则、重复用例处理及新旧用例关系边界、覆盖策略、自动化人工审核与技术校验边界等已确认。当前最终报告自动作为主报告；其他版本最终报告由用户按需多选；辅助报告不强制要求已完成 AI 总体分析；不单独读取或选择历史人工批次、自动化执行记录等原始资料。完整数据契约、接口实现细节及最终验收证据仍需在后续规格化/To Tickets 中落实。本文件持续更新，V0.3.0 总体 To Spec 尚未冻结。

## 1. 目标与业务定位

第 08 项是 V0.3.0 实际开发的 AI 功能，独立于未来 03–07 需求分析链路。

智能回归建议以**测试报告的总体分析**为起点，由用户主动触发 AI 进一步生成结构化、可追溯的回归建议。当前有效建议归属**项目级**并供该项目后续产品版本测试规划参考，但不建设可恢复的历史建议库，也不绑定到生成报告时的原测试组。

核心定位：
- 报告是建议生成的业务来源；
- 项目是当前有效建议的归属与可应用范围，不意味着提供历史建议列表；
- 后续产品版本是建议可能被采用的场景；
- 目标测试组由用户在后续规划时按实际情况决定，不预设为原测试组。

## 2. 已确认的业务规则

### 2.1 生成时机：用户主动触发

采用方案 B：
- 测试报告及其总体 AI 分析完成后，用户可以主动发起「生成智能回归建议」。
- 不在每次报告生成或总体分析完成时自动触发第二次 AI 调用。
- 用户决定是否需要进一步生成回归建议，避免对不需要规划回归的阶段性报告产生无意义调用。
- 第 08 项属于独立 AI 调用，遵守 V0.3.0 全局 AI 开关、AI 配置快照和统一 AI 任务运行约束；在本次调用界面提供就地取消/停止操作。
- 本期不接入统一任务队列或集中任务管理。若另一个 AI 调用正在运行，其他 AI 入口提示「当前有功能正在占用 AI，请稍后再试。」

### 2.2 智能回归输入范围（已确认）

- **智能回归的输入对象只有最终测试报告。** 不直接读取或要求用户单独选择历史人工测试批次、自动化执行记录、测试用例表、原始执行事件或其他独立历史测试资料。
- 用户当前打开并发起智能回归的最终测试报告，自动作为本次回归的**主报告**。主报告不需要再次选择，也不需要重新勾选它已经纳入的人工/自动化测试来源。
- 主报告以生成时保存的完整报告快照作为事实输入，其中已经包含用户当时选择的人工测试结果、自动化执行结果，以及最终报告生成时已纳入的其他报告资料（如有）；同时使用该主报告已成功完成的 AI 总体分析。智能回归直接读取报告快照，不再回头单独查询或拼接其下属人工批次、自动化执行记录。
- 用户可以额外多选同一项目内、其他产品版本的最终测试报告作为**辅助报告**。可以选择上一个版本、更早版本或之后版本，不限于紧邻的前后一个版本；不跨项目取数，也不能重复选择当前主报告。
- **辅助报告去重规则：** 主报告的最终报告快照中已经纳入的其他最终测试报告，视为主报告已包含的输入，不得再次作为辅助报告选择。系统在候选列表中自动排除这些报告；去重依据为最终报告唯一 ID，不按产品版本、测试组名称或报告标题去重。同一产品版本、同一测试组可以存在多份不同报告，只要报告 ID 不同且未被主报告快照纳入，就仍可选择。
- 去重不仅是前端展示规则。提交智能回归任务时，后端还必须根据主报告快照校验辅助报告 ID 列表，拒绝主报告自身 ID、已纳入主报告快照的报告 ID、跨项目报告 ID 及重复 ID，避免绕过候选列表造成重复输入。
- 辅助报告必须是已经生成并保存有效报告快照的最终测试报告。每份辅助报告作为一个完整报告输入，保留其产品版本、测试组、报告时间、事实快照及自身统计口径。**辅助报告不强制要求已经完成 AI 总体分析**：若已有成功完成的总体分析，可以一并参考；若没有，则直接依据该报告的事实快照进行跨版本比较。不得将辅助报告拆成单独的人工批次或自动化执行记录供用户选择。
- 当前主报告与辅助报告必须明确区分。主报告是本次回归的直接分析对象；辅助报告只用于跨版本比较和补充背景，不替代主报告，也不得改写主报告的事实、统计或结论。
- 辅助报告完全可选：用户不选择时，只分析当前主报告。系统不得自动勾选最近报告或自动扩展到其他历史记录；所有辅助报告均由用户明确添加。
- 辅助报告采用**标签式多选输入框（Tag-based Multi-select）**，不使用常驻的大型复选框列表。用户点击输入框后可检索/浏览可选最终报告，点击某份报告即将其加入已选标签；已选报告以紧凑标签显示在输入区域内，每个标签提供「×」移除操作。用户可连续添加多份报告；已选报告不再重复出现在可选结果中。移除标签即取消该报告的纳入。
- 默认界面只显示主报告、已选辅助报告标签和紧凑的搜索/选择输入，不展开完整报告清单。只有用户主动点击输入框时，才显示可选报告结果。候选结果必须排除主报告自身及主报告快照中已经纳入的最终测试报告。
- **空状态 A：当前项目没有其他可选的有效最终测试报告。** 在候选区域提示：「当前项目暂无可选的其他最终测试报告。你仍可以仅使用当前主报告生成回归建议。」这是正常的可选输入为空状态，不是错误；辅助报告本来就是可选项，不得因此禁用或阻止智能回归生成。
- **空状态 B：关键词搜索或版本筛选后没有匹配结果。** 在候选区域提示：「没有找到符合条件的报告，请调整搜索关键词或版本筛选。」提供清除搜索/筛选条件的操作。该状态只表示当前候选展示结果为空，不代表项目没有报告，也不影响智能回归生成。
- 两种空状态均不得清空或移除用户此前已选的辅助报告标签；用户调整或清除搜索、筛选条件后，已选标签继续保留。两种空状态都不自动加入报告、不报错，也不改变主报告。
- 每条候选辅助报告展示以下五项基本信息，帮助用户快速识别，不需要打开报告详情：
  1. **产品版本**：例如 V1.1。
  2. **测试组**：例如主板兼容性测试。
  3. **报告编号**：例如 #89。
  4. **报告生成时间**：明确显示日期和时间。
  5. **AI 总体分析状态**：展示该报告实际状态，仅作辅助判断，不作为选择门槛。辅助报告没有 AI 总体分析、分析失败或尚未完成，均不因此禁止选择；只要最终报告及事实快照有效即可。
- 候选报告默认按**报告生成时间倒序**排列，最新生成的报告优先显示。
- 输入框支持关键词搜索，搜索范围包括**产品版本、测试组名称、报告编号**；不要求用户记忆报告 ID。
- 支持按**产品版本**筛选候选报告。关键词搜索与版本筛选可以同时生效，结果取两者条件的交集。
- 搜索、筛选和排序只改变候选列表的展示，不会自动将任何报告加入分析范围；只有用户主动点击某条候选报告，该报告才加入已选标签。
- 搜索结果必须继续遵守当前项目范围、有效最终报告快照要求，以及主报告自身/主报告已纳入报告的去重规则。
- 所有报告限定在当前项目内，可以跨该项目的其他产品版本，不跨项目。
- 不要求用户输入新需求，不依赖未来的需求文件导入或 03–07 需求分析链路。

**与最终报告生成阶段的区别：** 2.3 节定义的是用户生成一份最终测试报告时，如何选择该报告所包含的人工/自动化结果及其他报告资料；这些选择已经固化在最终报告快照中。智能回归阶段只选择当前主报告以外的其他最终报告，不重复选择主报告内部的原始来源。

### 2.3 最终测试报告的来源选择（本轮已确认的交互原则）

- 最终报告工作区分别提供自动化执行结果、人工测试结果的下拉选择控件；这不是把同一测试组的所有结果自动纳入，也不是用复选框列出整张用例表。
- 自动化执行结果下拉为单选：一次最多选择一条自动化执行记录，另提供明确的「无（不参与本次报告）」选项。
- 人工测试结果下拉为多选：可以同时选择多个人工测试批次，另提供明确的「无（不参与本次报告）」选项。选择「无」时清空已选批次；选择任意具体批次时自动取消「无」。
- 自动化与人工来源相互独立；任一类别选择「无」只排除该类别，不影响另一类别的选择。选择「无」即明确表示该类来源不参与本次报告，不得在生成时回退到最新记录或自动补入其他记录。
- 自动化和人工来源相互独立：例如人工下拉选择某一次批次、自动化下拉选择「无」，本次报告只纳入该人工批次；同一测试组中的其他批次、执行记录和用例不得因为属于同一测试组而被自动加入。
- 选择某次人工批次或自动化执行记录后，纳入该来源记录中应报告的完整结果状态，包括通过、失败、阻塞和未执行；「只分析选中部分」指来源范围受用户选择限制，不是只分析通过项。
- 前端选择状态必须区分「尚未初始化/采用当前默认选择」与「用户明确选择无」。明确选择无后，刷新或重新加载不得静默恢复为最新记录。
- 历史测试报告也可以作为可选来源，并允许用户多选；用户未选择任何历史报告时，表示本次不纳入历史报告。
- 当前版本的测试统计只根据本次选定的当前版本人工批次和自动化执行记录计算。历史报告作为独立历史对照资料展示，并可供 AI 总体分析综合参考；历史版本的测试数量、通过率、失败数等必须保持各自版本口径，不得与当前版本数据相加或混算成当前版本统计。
- 历史报告应保留来源产品版本、报告标识及原有统计快照，展示时明确标记历史版本。具体展示布局继续细化。
- 上述历史报告选择发生在「生成最终测试报告」阶段。报告生成后，其已选择的来源都属于该最终报告的固定快照；后续发起智能回归时，不得再次要求用户选择这些报告内部的人工批次或自动化执行记录。智能回归可选的辅助输入是当前主报告以外、同项目其他产品版本的最终测试报告。
- 当前 V0.2.0 前端已经分别使用自动化执行记录和人工测试批次下拉框，但没有「无」选项，且空选择会回退到最新记录；后续实现需按以上规则扩展。后端 `FactReportCreate` 当前只接受一个自动化执行 ID 和人工批次 ID 列表，且要求至少选择一项，历史报告来源契约尚不存在。

### 2.4 回归建议的生成入口与应用去向

- 「智能回归」入口位于最终测试报告工作区，与「生成最终报告」并列，不放在原测试组详情操作区。按钮在该工作区始终显示，固定占据布局位置；不因报告或 AI 状态变化而动态插入、移除，避免页面布局跳动。
- 按钮可见不代表始终可用。未生成最终测试报告、报告总体 AI 分析尚未成功完成、全局 AI 关闭或当前 AI 正被其他功能占用时，按钮保持可见但禁用；满足前置条件后才启用。
- 禁用状态应保留按钮名称和可辨识度，并在按钮附近提供明确、与当前状态对应的原因提示，例如「请先生成最终测试报告」「等待报告 AI 总体分析完成」「请先开启 AI」「当前有功能正在占用 AI，请稍后再试」。不得通过隐藏按钮表达暂不可用。
- 报告总体 AI 分析失败或被取消时，不得直接启用智能回归；需先获得有效完成的报告总体分析结果。
- 用户在当前主报告及其总体分析完成后主动触发回归建议生成；当前报告自动纳入，不重复选择其内部来源。用户可额外多选同项目其他产品版本的最终测试报告作为辅助输入；不读取其他独立历史资料。
- 回归建议结果采用「回归分析说明 + 结构化回归用例表」：说明区用文字解释主要风险、历史变化、建议回归原因及重点；用例区以表格逐条呈现可执行的回归候选，不以长段文字代替用例。
- **回归分析说明固定采用四段式结构：**
  1. **总体风险判断**：概括当前主报告反映的整体风险情况，并结合用户选择的辅助报告说明跨版本风险判断。没有选择辅助报告时，只依据主报告分析，不得虚构跨版本比较结论。
  2. **重点变化**：指出值得关注的模块、功能或行为变化，并说明判断依据来自哪些报告、版本或具体发现；只陈述报告事实及有依据的分析，不臆测未提供的版本变更。
  3. **回归重点**：说明建议重点验证哪些方面、为什么需要验证，以及需要关注的风险表现。该部分解释回归方向，不要求每一段文字都与某一条用例一一对应。
  4. **建议总结**：汇总本次建议覆盖的模块范围及回归用例总数，帮助用户快速了解建议规模；统计必须来自本次实际生成的回归用例，不得估算或编造。
- 四段式说明与下方回归用例表是两个相互补充的区域：说明区负责解释整体判断和回归思路；用例表负责提供可单独执行、勾选和应用的具体用例。不得用分析文字替代结构化用例，也不要求每段说明都对应一条用例。
- **回归用例表一行代表一条独立、完整、可执行的回归测试用例。** 每行都应能被单独理解、勾选、应用和后续执行，而不是仅代表一个模糊风险点或一段分析文字。
- 如果同一条回归建议实际包含多个彼此独立的测试场景，应拆分为多行，每个场景形成一条独立用例；不要把多个可分别执行、可分别判断结果的场景塞进同一行。
- 单条测试用例内部为完成同一测试目的所必需的多个步骤，应保留在同一行的步骤字段中，不要把一条连贯测试流程机械拆成多条用例。
- 每一行都可以独立勾选、筛选和批量应用；用户可以只采用其中部分回归用例，不要求整组建议一起接受。
- 回归用例表沿用现有用例表的勾选交互：表格最前面设置选择列，每条建议行前有复选框，表头复选框用于全选当前筛选结果；同时提供「反选当前筛选结果」和「清空选择」操作。不得另造一套不同的选择交互。
- 回归用例采用**一张连续表格**展示，不按模块拆分成多个独立表格或可折叠分组。模块作为普通字段保留在每一行，并通过模块筛选查看指定模块的用例。
- 模块筛选与其他筛选条件共同作用于同一张表格；全选/反选仍只作用于当前筛选命中行，筛选外已选项继续保留。不得因模块切换而重置或丢失用户此前的选择。
- 批量选择操作的作用范围严格限定为当前筛选结果：全选只选中当前筛选命中的行；反选只切换当前筛选命中行的勾选状态，不影响筛选结果之外的已选项。用户切换筛选条件时，之前在筛选结果之外的选择继续保留，便于跨模块累积选择。
- 表格持续显示建议总数、当前筛选命中数及已选总数，避免用户误以为全选覆盖全部建议或忽略筛选外仍被选中的项目；提供「清空选择」以一次清除本轮全部勾选。
- 「加入用例表」和「加入指定测试组」是回归建议表旁的批量应用操作：用户完成勾选后，点击其中一个按钮，系统只处理最终已勾选的建议；未勾选项仍保留在当前回归建议中，不写入目标资产。按钮名称使用「加入用例表」「加入指定测试组」，不使用含义不清的「回归到……」命名。
- 新一轮回归建议成功替换旧建议时，旧批次选择状态一并清空，不得将旧选择带入新批次。
- 如果被选中的回归建议与目标版本已有用例标题、步骤或其他内容相同，也不得自动覆盖、更新或合并原用例。该回归建议作为一条独立的新用例记录加入目标资产，保留原用例及其历史身份；新增记录的 `test_type` 仍必须为「回归测试」。
- 回归用例表采用**主表 + 行详情**结构，避免长步骤和长文本撑宽表格，同时保留完整可执行信息。
- **主表直接展示字段：**
  1. 选择框：每行独立勾选；表头复选框及全选/反选规则沿用既有约定。
  2. 用例标题：清晰描述单条回归测试的目的。
  3. 执行方式：人工 / 自动化。
  4. 所属模块。
  5. 优先级。
  6. 回归原因：简要说明为何需要回归，较长依据放入行详情。
- **行详情：** 用户展开/点击某一行后查看该用例的完整内容，包括前置条件、测试输入、测试步骤、预期结果，以及精简的「来源依据」区域。来源依据只保留三项：①来源报告：报告编号、产品版本，并可点击打开对应报告；②关联发现：报告中与本用例相关的风险/异常摘要；③推荐原因：简要说明 AI 为什么据此建议该回归用例。有多个来源时按来源分别列出对应发现，保持紧凑；不展示整份报告、不重复冗长报告内容，也不在主表额外增加来源列。
- 执行方式用于决定系统内部写入路径，不是用户需要选择的应用去向。
- 必须区分两个字段概念：`case_type` 表示执行方式（人工/自动化）；`test_type` 表示测试类型（如功能、性能、兼容性）。本次由智能回归生成并正式加入用例资产（无论通过加入用例表或加入指定测试组）的所有用例，无论标题、步骤或其他内容是否与已有用例相同，`test_type` 均必须明确设置为「回归测试」，不得因其他字段未变化而沿用旧测试类型。
- 对于与目标版本已有用例内容重复的回归建议，不自动覆盖、更新或合并原用例；按独立的新用例记录保存，原用例保持不变。
- 新回归用例与目标版本中已有的相似/重复用例之间**不建立额外关联关系**：不复用旧用例 ID，不建立新旧用例的父子、映射或关联记录。用例的来源追溯通过本条建议的来源报告及其关联发现完成即可。若自动化回归用例需要现有数据模型中的 `source_test_case_id`，该字段只关联本次新建的来源用例记录与本次新建的自动化记录，不得指向目标版本中既有的旧用例。
- 用户应用到用例资产时只选择「加入用例表」，不再分别选择人工表或自动化表。系统依据每条建议的执行方式自动分流；同一批建议可以同时包含人工和自动化用例，并分别进入对应的现有用例管理路径。
- 选择「加入用例表」时，用户必须明确选择目标产品版本；不得默认使用来源报告所在版本。选择「加入指定测试组」时，用户只需选择目标测试组，该测试组所属产品版本即为目标版本，不再重复要求选择产品版本；同样不得默认使用来源报告的原测试组。
- 现有实现中，人工/原始用例保存在 `source_test_cases`，`test_type` 是该来源用例字段；自动化用例保存在 `automation_test_cases`，并通过 `source_test_case_id` 关联来源用例。`SourceTestCase.case_type` 表示执行方式，当前查询实现是在存在关联 `automation_test_cases` 记录时标记为 `automation`，否则为 `manual`；自动化记录的 `validation_status` 是单独字段。当前查询对自动化身份的判断与模型注释存在口径差异，后续实现前必须核实并统一；不能把 `test_type`、`case_type`、人工审核状态和技术校验状态混为一谈。
- 自动化回归建议加入正式资产时，系统必须在后台建立正式来源用例记录，并创建关联的 `automation_test_cases` 记录；自动生成用例编号并维护 `source_test_case_id` 关系。用户不需要为了建立这层数据关系，再单独进入人工用例表执行一次导入或审核。来源记录的 `test_type` 必须为「回归测试」。
- 「加入指定测试组」时，用户选择目标测试组即可确定目标产品版本。测试组内人工/自动化成员按各自执行方式进入对应关系，不改变原有身份和技术校验规则。
- 回归建议生成后不自动写入任何正式资产。用户明确选择一个应用去向并确认：①「加入用例表」；②「加入指定测试组」。整批建议统一选择一个去向。选择「加入用例表」必须明确选择目标产品版本；选择「加入指定测试组」时，通过目标测试组确定产品版本，不重复选择版本。


- **人工审核确认与系统技术校验分离。** 用户点击「加入用例表」时，该明确应用动作即视为对所选自动化回归建议完成了人工审核；用户选择「加入指定测试组」且所选建议包含自动化用例时，系统弹出确认：「是否将 N 条自动化回归用例直接加入自动化用例表，并同时加入当前测试组？」用户选择「直接加入」即视为已完成人工审核和加入授权，不再要求用户进入自动化用例表进行第二次审核、勾选或转移。若没有选中自动化建议，不显示此弹窗。
- 用户在上述测试组确认弹窗选择「暂不加入」时，本次选中的人工用例仍可正常加入测试组；自动化建议不写入自动化用例表、不加入测试组，并继续保留在当前回归建议中，用户之后可单独应用。
- 用户确认直接加入后，系统自动创建来源用例及其关联自动化用例记录，写入「回归测试」类型，维护来源关联并执行现有确定性技术校验。人工确认代表业务审核通过，不代表跳过技术校验；`validation_status` 不得用来代替人工审核记录。需要持久化可追溯的确认信息（至少包含确认状态、确认时间及确认来源），与技术校验结果分开保存。当前 `AutomationTestCase` 模型只有 `conversion_status`、`validation_status` 等字段，没有独立的人工审核标记；实现时需新增明确的审核记录字段或等价审计记录，不得把模型置信度或技术校验通过状态解释为人工审核。
- 自动化技术校验通过后，系统直接将该自动化用例加入用户当前选择的测试组，不再增加人工审核环节。若技术校验失败，记录仍保留在自动化用例表并显示具体校验原因，但暂不加入测试组；不要求用户重新进行人工审核，修正后只需重新执行确定性校验。
- AI 生成阶段必须直接按现有人工来源用例和自动化用例的数据契约生成，并在发布建议前完成结构及必填字段校验。常规格式缺失或字段不匹配应在生成阶段拦截，不得把格式适配工作转嫁给用户；此类问题属于建议生成失败，不属于加入失败。
- 正式应用前预检目标产品版本、目标测试组是否存在且仍有效、目标版本归属是否匹配、自动化用例关联及其他既有准入条件。预检不通过时阻止本次应用并说明原因，不创建正式记录；这属于应用前置条件不满足，不记为加入失败。
- 批量应用采用逐条独立提交：某条用例的来源记录、自动化记录及必要关联必须保证单条记录内部一致；同一条记录创建过程发生完整性/关联写入异常时，回滚该条未完成的写入，避免留下半条或孤立数据。其他已经成功的用例不回滚。
- 用户可见结果区分三类：①「已加入」——目标正式用例资产及所选测试组关联均已完成；②「已保存，待校验」——自动化记录已进入自动化用例表，但尚未通过确定性校验，因此暂不加入测试组，必须同时显示具体校验结果/原因；校验通过后由系统自动完成已授权的测试组加入，不再要求二次人工审核；③「加入失败」——发生数据库、连接、事务或关联写入等非预期技术异常，导致该条用例未完成目标应用。失败详情必须说明发生环节、具体原因、是否已经创建正式记录及下一步处理方式。
- 如果正式自动化用例记录已经成功创建，但后续写入测试组成员关系失败，不得重新创建来源/自动化记录；应保留已创建记录，将结果标记为「加入失败（测试组关联未完成）」并仅重试缺失的测试组关联。所有重试均须幂等，不能重复创建已成功记录或重复添加成员。
- 自动化技术校验失败本身不是「加入失败」：自动化记录保留在自动化用例表，显示「已保存，待校验」及校验未通过的具体原因，暂不加入测试组。用户不需要重新人工审核；修正后重新执行确定性校验，通过后自动入组。
- 重复标题、步骤或其他内容不构成失败；按已确认规则独立新增。目标版本/测试组不存在或不匹配等可预检问题必须在正式写入前阻止并解释，不得伪装成数据库加入失败。
- 建议表对每条记录持续展示应用结果。已加入记录保留「已加入」状态且不再允许重复应用；已保存但待校验的自动化记录保留在自动化用例表并展示校验原因；真正加入失败的记录保留在当前回归建议中，展示失败环节、原因和是否已有正式记录，并提供针对未完成步骤的单条重试。未选择的建议继续保持待处理。

### 2.5 回归建议的一次性展示与覆盖

- 回归建议是本次报告分析产生的一次性成果，不建设项目级回归建议历史库，不提供历史建议版本列表或恢复入口。
- 当前回归建议由文字分析说明和结构化回归用例表组成。生成后供用户查看，并允许用户选择目标位置应用；除此之外不增加建议状态流转、持续编辑、反复审核或后续维护工作流。
- 用户应用建议后，正式写入人工用例表、自动化用例表或测试组的内容，成为对应模块的正式数据，按原有数据生命周期保留；建议展示区不因此变成正式用例的替代存储。
- 采用用户已确认的 B 方案：只有新一轮回归建议完整生成成功、结构校验通过并可正常展示后，才整体替换当前建议。开始生成、调用中、取消、失败或结果结构校验失败时，旧建议继续保留，不提前清空。
- **已确认的业务特例（DEC-08-30，2026-11-17）**：08 不采用 01 同条件重试的「覆盖上一次结果」复选框，不生成可恢复的多份有效回归建议。相同输入重试时仍提示可能重复并提供「重新执行／取消」；无论是否同条件，只有新建议完整生成、通过结构校验且成功保存后才替换项目唯一当前建议。失败、超时、取消、中断或校验/保存失败均保留旧建议及已应用正式用例。运行中重试须先完成旧调用取消收尾，不并发执行；08 的全局运行锁、就地取消和审计仍遵守 01，其他 AI 业务沿用 01 通用重复执行规则。- 新建议成功替换后，旧建议不再提供查看、恢复或重新应用入口；已经应用到正式用例表或测试组的内容不受影响。
- 建议结果仍需在生成当次记录主报告及用户实际选择的辅助报告清单，以便用户理解当前建议的依据；来源记录只说明本次使用了哪些最终报告，不意味着保留可恢复的历史建议快照。
- **已确认的应用规则**：用户明确选择目标产品版本并使用「加入用例表」，或者明确选择已有目标测试组并使用「加入指定测试组」；后一操作的目标版本由该组确定。不自动创建、复制或重组测试组，也不默认选择来源报告原测试组。未来新建/重组测试组继续使用现有测试组管理功能，不另外引入自动规划链路。

## 3. 与 V0.2.0 现有报告能力的关系

当前事实报告 AI 总体分析的输出结构 ReportAnalysisOutput 已包含 risks、additional_verifications、regression_recommendations 和 stage_recommendation。

其中现有 regression_recommendations 是带有证据引用的文本型报告分析条目。它可以作为第 08 项的输入依据，但不能直接等同于第 08 项要生成的结构化、可追溯、项目级回归建议快照。

第 08 项应与现有事实报告及总体分析保持来源关联，不得：
- 改写事实报告的原始测试事实、执行记录或既有报告快照；
- 将原有文本建议直接伪装成已审核、可直接发布的测试用例；
- 因生成回归建议而自动修改原测试组；
- 将来源报告所属测试组当作下一轮默认目标测试组。

## 4. 现有实现基础（代码核验）

- 后端 FactReport 已包含 test_group_id、product_version_id、事实快照及 AI analysis；报告因此可以追溯到生成时的测试组与产品版本。
- ReportAnalysisOutput.regression_recommendations 当前为 ReportAnalysisItem[]，条目包含 content 和 evidence_refs。
- 报告 AI 分析已有运行批次、状态、取消/后台执行相关基础，具体复用方式须结合 01「全局 AI 开关与单次调用控制」的单活动调用锁和就地取消规则核验；本期不建设统一 AI 任务管理中心。
- 人工测试结果批次和自动化执行记录是生成最终报告时使用的底层来源；智能回归不把它们作为独立输入，而是通过最终报告已保存的事实快照继承这些结果。其他版本的辅助输入同样必须是完整最终报告。
- 上述现有结构只证明可复用的数据来源，不代表第 08 项的项目级回归建议快照、选择界面或应用流程已经实现。

## 5. 输入异常、生成失败与取消（已确认）

- **主报告不可用**：当前最终报告不存在、事实快照缺失/不完整或 AI 总体分析未成功完成时，不允许开始智能回归；明确指出主报告不满足的条件。不得用辅助报告代替主报告，也不得静默修复或跳过缺失快照。
- **辅助报告不可用**：选择后如发现某份辅助报告事实快照缺失、损坏或已不可用，列出具体报告编号及原因，并要求用户选择「移除该报告后继续」或「取消本次生成」。不得静默跳过该报告或替换成其他报告；后端提交时再次检查所有输入。
- **模型调用失败或用户取消**：本轮不产生或展示不完整的新建议，不覆盖已有有效回归分析说明和用例表，不改变本轮此前已应用到正式用例表/测试组的记录。给出明确失败/取消反馈，不将异常表示为成功，也不自动重试。
- **成功替换边界**：只有新一轮模型输出全部完成、通过结构校验并可完整展示时，才统一替换上一轮建议，继续沿用第 2.5 节的 B 策略。辅助报告为空时按已确认规则仅分析主报告。

| R08-02 | 有效 `R-M` 且不选择辅助报告 | 仅使用主报告及其成功分析；不自动添加历史报告，不凭空宣称跨版本变化 |

| R08-04 | 搜索、按版本筛选、切换筛选、无候选与无匹配结果 | 候选默认生成时间倒序；两种空状态提示不同；筛选变化不丢已选标签 |
| R08-05 | 尝试选择主报告、已内嵌报告、重复 ID 或其他项目 `R-X`；构造绕过前端请求 | 候选排除、后端再次拒绝非法 ID；不泄漏或读取跨项目资料 |
| R08-06 | 已选 `R-BAD` 在提交时失效 | 显示具体报告编号/失效原因；仅在用户选择「移除该报告后继续」后继续，否则取消且旧建议保留 |
| R08-07 | 生成合规 Mock 建议 | 四段说明完整且统计来自实际候选；每行独立可执行；主表字段及行详情完整；来源报告与具体发现可追溯、无伪造证据 |
| R08-08 | 模型输出缺少必填步骤/预期、来源无效、结构不完整 | 发布建议前校验失败，不展示半成品、不应用任何新候选、不替换旧有效建议 |
| R08-09 | 模块、执行方式筛选下全选/反选、切换筛选、清空 | 一张连续表；操作只影响当前筛选行，筛选外已选项保留；总数/命中数/已选数准确 |
| R08-10 | 勾选部分人工/自动化建议，选「加入用例表」并指定目标 V1.3 | 只加入已选项；`case_type` 正确分流，新增来源记录 `test_type=回归测试`；未选项不写入正式资产 |
| R08-11 | 选「加入指定测试组」G-T | 目标版本从 G-T 归属确定；不重选来源报告原组，不自动建组/复制旧版本组 |
| R08-12 | V1.3 已有内容相似用例；已成功行再次应用 | 原用例不被覆盖/合并，不额外建立新旧用例关联；新建议独立入库，重复操作不产生重复正式记录 |
| R08-13 | 自动化建议应用并分别通过/不通过确定性技术校验 | 新建来源用例和关联自动化记录，`source_test_case_id` 指向本次新建来源；人工确认可审计且独立于技术校验；失败留表待校验而不入组 |
| R08-14 | 对测试组自动化确认选择「暂不加入」 | 自动化建议留在建议区不正式写入；同次选中的人工建议仍可按授权加入；不再要求额外审核 |
| R08-15 | 混合批量写入：单条失败、用例已建但组关联失败、随后重试 | 已成功项不回滚；未完成单条写入无孤儿记录；仅重试失败环节，展示原因与已保存状态，重复重试幂等 |
| R08-16 | 已有有效建议时模型失败、超时、取消、截断；再成功生成一轮 | 异常不覆盖旧建议及已应用资产；新结果完整且结构合格后才一次性替换，旧选择不带入，无历史恢复入口 |
| R08-17 | AI 关闭、其他业务占用、同一操作重复触发、刷新后返回 | 遵守 01 全局锁和就地取消规则；不会并发启动第二项 AI 任务；运行状态与当前有效结果可复核 |
| R08-18 | 修改当前版本 `ai_context` 后生成，运行期间再次修改 | 输入指纹及运行快照使用启动时的版本说明；同次后续阶段不混入新文本，下一次调用才读取新说明 |
| R08-19 | 使用 27 寸 4K 与 13 寸笔记本逐项操作 | 主表所有列、筛选、行详情、选择及应用按钮均保留；使用换行/重排/局部滚动而非删除关键控件 |
| R08-20 | 相同输入重试和运行中重复点击；分别模拟成功、失败、取消、校验或保存失败 | 提示重复并提供「重新执行／取消」，无覆盖复选框；运行中重新执行先完成旧调用取消收尾；完整成功后一次性替换唯一有效建议并清除旧勾选，异常保留旧建议及已应用正式用例，不产生第二份可恢复建议 |

### 6.3 真实模型验收（必须与 Mock 分开记录）

- 使用**已保存且连接验证有效**的实际模型配置和脱敏、可用于调用的最终测试报告，在全局 AI 开启且无其他活动调用时，分别完成「仅主报告」和「主报告 + 有效辅助报告」两条真实生成路径。
- 核验真实模型返回的四段分析、每条建议的可执行性、人工/自动化标记、来源报告和关联发现的事实一致性，以及加入正式资产后 ID/目标版本/测试组的正确性。不得用接口 HTTP 200 或模型输出非空文字替代质量与证据核验。
- 真实模型输出非确定性：**不要求固定用例数量、固定标题或逐字一致**；记录实际数量、典型内容、引用定位、人工发现的问题和最终判定。事实无证据、步骤不可执行、凭空比较版本均不得按通过处理。
- 对真实模型验收记录至少保留服务商/模型名称、运行时间、报告夹具标识、脱敏输出和人工核验结论；与 Mock 测试报告分开。失败/超时/取消、事务和幂等故障以可控 Mock/故障注入复核，不要求在线模型稳定复现故障。

### 6.4 持久化与追溯最低证据

- 当前有效建议可追溯**项目、主报告 ID/所属版本、实际辅助报告 ID 列表、生成时采用的事实报告快照标识/可核验摘要、本次 `ai_context` 快照指纹、AI invocation ID/状态、四段说明及结构化建议行**。不将后来修改的报告、版本说明当作当次已使用的输入。
- 当前建议的保存和展示用于一次性查看与批量应用，**不建设历史建议库、旧结果恢复入口或复杂持续编辑工作流**；新结果成功才替换当前结果，失败/取消保留原结果。
- 已应用建议应可追踪目标版本/测试组、实际新建来源用例 ID 和自动化用例 ID（如有）、用户对自动化建议的审核确认与时间、技术校验/应用状态，以及失败时已完成与待重试的步骤；检查目标组成员不重复且没有半条记录。
- 验收证据包括生成前后**报告原始事实、来源测试组和旧用例保持不变**的对照。具体数据表/API、快照摘要字段、事务方案由 To Tickets 结合现有代码确定，不提前宣称已实现。
- 运行日志和验收截图必须脱敏，不记录或公开 API 密钥、Authorization、完整敏感 Prompt、未经授权的测试证据。

## 7. 明确不做

- 不将回归建议绑定到生成报告时的原测试组。
- 不假设下一版本测试组结构与当前相同。
- 不自动把旧版本测试组复制为下一版本测试组。
- 不自动把旧版本用例 ID 写入新版本测试组。
- 不自动执行回归测试，不改变任何原始测试结果或事实报告。
- 不依赖尚未实现的 03–07 需求分析、风险分析和推荐用例链路。
