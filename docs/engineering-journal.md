## 2026-08-21：任职期间旧项目存在权属与保密风险

- **问题现象**：原计划考虑复用任职期间由本人借助 AI 开发的测试工具和数据分析项目。
- **影响范围**：代码、Prompt、数据、报告、界面和公开仓库都可能涉及公司权属或未公开信息。
- **错误证据**：旧项目与本职测试工作及公司产品直接相关，且可能使用公司资料和设备数据。
- **排查过程**：区分“由本人完成”与“权利归本人”，核对职务软件的一般权属规则。

- **解决方案**：采用洁净重写，只复用通用经验；使用虚构设备、公开格式和合成数据。
- **验证方法**：建立仓库合规清单，检查公司名称、接口、代码片段、数据、截图和密钥。

## 2026-08-21：错误假设原始时间戳应天然一致

- **开发阶段**：时间同步方案设计。
- **问题现象**：初始方案把正常场景定义为四路视频与 IMU 共享完全一致的时间轴。
- **影响范围**：会掩盖 POC/EVT 阶段真实存在的固定偏移、抖动和漂移，也无法展示对齐优化过程。
- **错误证据**：实际工程中原始数据的时间戳并不保证一致，时间对齐本身就是优化和测试对象。
- **排查过程**：重新区分原始时间戳、时间对齐、对齐残差和画面内容同步。
- **根本原因**：把最终目标状态误当成输入数据的先验条件。
- **解决方案**：同时保留对齐前后两套结果，首版实现固定偏移和线性漂移校正。
- **验证方法**：生成带已知偏移和漂移的场景，验证对齐参数及残差是否符合故障真值。
- **回归检查**：确保校正结果不会覆盖原始证据，且画面同步拥有独立检查结果。
- **经验与面试表达**：测试平台不仅判断结果，还要保留产品从 POC 到 EVT 的改进证据。

## 2026-08-22：本地与 CI 测试入口的 Python 导入路径不一致

- **开发阶段**：Ticket 01 工程骨架。
- **问题现象**：在 `backend/` 内运行健康 API 单测通过，从仓库根目录执行相同测试却无法导入 `app`。
- **影响范围**：README 的统一验证命令和 GitHub Actions 会在收集测试时失败。
- **错误证据**：根目录运行 Pytest 报 `ModuleNotFoundError: No module named 'app'`。
- **排查过程**：对比两种工作目录，确认测试本身和 FastAPI 依赖均正常，差异来自包发现及测试导入路径。
- **根本原因**：初始 `pyproject.toml` 没有声明 `app` 包发现，也没有为 Pytest 声明项目包路径。
- **解决方案**：显式配置 setuptools 查找 `app*`，并将 Pytest `pythonpath` 固定到后端项目根。
- **验证方法**：从仓库根目录执行 `backend/.venv/Scripts/python.exe -m pytest backend/tests`。
- **回归检查**：同一命令进入 CI，避免本地通过、CI 收集失败。
- **经验与面试表达**：测试入口必须与 CI 的工作目录一致，环境差异要和业务断言失败分开记录。

## 2026-08-22：固定前端版本后依赖目录与锁文件不一致

- **开发阶段**：Ticket 01 工程骨架。
- **问题现象**：把首次解析的 `latest` 改为确切版本后，pnpm 在非交互终端拒绝自动重建 `node_modules`。
- **影响范围**：前端测试、类型检查、格式检查和构建均无法启动。
- **错误证据**：pnpm 返回 `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`。
- **排查过程**：检查 `pnpm-lock.yaml` 与 `package.json`，确认版本内容一致，只有现有依赖目录的安装元数据过期。
- **根本原因**：为保证可重复安装而固定版本后，没有立即按新锁文件重建本地生成目录。
- **解决方案**：使用 `pnpm install --force --frozen-lockfile` 仅重建可恢复的项目依赖目录。
- **验证方法**：重新执行 Vitest、TypeScript、Prettier 和 Vite build。
- **回归检查**：CI 使用 `pnpm install --frozen-lockfile`，禁止漂移安装。
- **经验与面试表达**：锁文件和本地生成目录是两层状态；前者正确不代表后者已经同步。

- **影响范围**：若一次开放全部字段，会提前实现后续参数校验与数据生成 ticket；若只保存名称，又不能表达任务配置。

- **解决方案**：当前契约只接受名称、固定 `quick` 模式和固定 `normal` 场景，并持久化初始 `draft` 状态。
- **验证方法**：API 测试覆盖创建、详情、列表刷新和非法名称；前端测试覆盖保存、重新加载与前置校验。
- **回归检查**：完整测试为 Pytest 6 项、Vitest 4 项通过，类型、格式、构建和安全扫描通过。
- **经验与面试表达**：先用窄契约跑通可验证链路，再由后续迁移扩展字段，可以降低返工并保持 ticket 边界清晰。

## 2026-08-22：开发机缺少系统 FFmpeg

- **开发阶段**：Ticket 03 正常场景真实文件生成。
- **问题现象**：开始实现前执行 `ffmpeg -version` 和 `ffprobe -version`，PowerShell 均报告命令不存在。
- **影响范围**：无法满足真实生成 H.264 短视频，也会让本地与 CI 对系统预装状态产生差异。
- **错误证据**：PowerShell 返回“The term 'ffmpeg' is not recognized”。
- **排查过程**：区分代码错误与环境依赖错误，并比较手工安装系统程序和项目固定二进制依赖两条路线。
- **根本原因**：规格选定 FFmpeg，但 Ticket 01 的运行骨架没有为每台执行环境提供可复现的 FFmpeg 可执行文件。
- **解决方案**：固定 `imageio-ffmpeg==0.6.0`，通过参数列表调用其 FFmpeg，不拼接 shell 命令；不引入本 ticket 不需要的 ffprobe。
- **验证方法**：公开 API 生成 MP4，并用同一工具读取元数据确认 codec 为 `h264`；真实 HTTP 冒烟生成 134611 字节视频。
- **回归检查**：Pytest 7 项、Vitest 5 项、类型、格式、生产构建和安全扫描全部通过。
- **经验与面试表达**：媒体测试既要验证业务结果，也要把外部工具版本纳入可重复环境，避免“我的机器能跑”。

## 2026-08-22：多通道真实性与长稳生成速度冲突

- **开发阶段**：Ticket 04 可配置多通道合成文件生成。
- **问题现象**：规格允许 300 秒、四路 1080p、60 FPS；若全部真实生成，本地演示时间和文件规模不可控。
- **影响范围**：任务创建、FFmpeg 执行时间、磁盘占用、重复运行稳定性及报告真实性。
- **错误证据**：按像素帧估算，四路 1080p、60 FPS 即使只生成 5 秒也达到 24.88 亿像素帧。
- **排查过程**：拆分“真实短媒体”和“长稳资源趋势”，分别评估演示价值、确定性和生成成本。
- **根本原因**：视频真实性与长时间资源变化服务不同验证目标，不应强制使用同一种时间来源。
- **解决方案**：真实媒体最长生成 5 秒；更长请求由设备状态 CSV 保留完整虚拟时间线；以 6 亿像素帧为
  本地安全上限，在前端与 API 入队前同时拒绝超限组合，并在产物及运行元数据中标明来源。
- **验证方法**：API seam 真实生成双路 MKV 和 JSONL；相同种子两次运行的全部 SHA-256 与重复性指纹一致；
  300 秒请求记录 5 秒真实媒体和 300 秒虚拟趋势；超限组合返回 422 且不创建任务。
- **回归检查**：Pytest 29 项、Vitest 8 项、Ruff、TypeScript 和 Prettier 检查通过。
- **经验与面试表达**：真实性不是把所有数据都做大，而是明确每类证据的来源、用途和成本边界。

## 2026-08-22：取消状态与生成证据存在并发收尾窗口

- **开发阶段**：Ticket 05 排队与安全取消。
- **问题现象**：执行中取消已立即返回“已取消”，但首次 API 测试马上查询时产物仍为空。
- **影响范围**：若工作线程直接退出会丢失已生成证据；若取消接口等待 FFmpeg 完成又会延迟取消反馈。
- **错误证据**：首轮单文件 Pytest 为 3 项通过、1 项失败，失败断言是取消响应后的 `artifacts == []`。
- **排查过程**：对照取消请求、FFmpeg 生成完成和阶段边界保存的时序，确认状态更新先于证据安全收尾。
- **根本原因**：取消状态和外部进程当前步骤的结束不是同一时刻，接口不能假设两者同步完成。
- **解决方案**：SQLite 原子终态阻止工作线程覆盖取消；当前生成步骤结束后只补存产物，不再进入检查阶段。
- **验证方法**：公开 API 先验证取消立即生效，再轮询到已取消记录保留非空产物。
- **回归检查**：覆盖排队取消、执行中取消、串行执行、重新执行和重启恢复，并运行完整测试。
- **经验与面试表达**：安全取消是协作式状态机，需要区分“停止接收后续工作”和“当前步骤完成收尾”。

## 2026-08-23：VFR 平均帧率不能定位真实掉帧窗口

- **开发阶段**：Ticket 06 单路视频掉帧场景。
- **问题现象**：使用 VFR 保留掉帧后的时间戳间隙时，媒体元数据给出的平均帧率从配置的 15 FPS 降为
  12 FPS；若用该平均值反推帧间隔，异常窗口起点会被算成 0.817 秒，而预定注入位置是 0.800 秒。
- **影响范围**：掉帧总数仍可由预期帧数与实际帧数得到，但异常时间窗口会偏移，故障真值对照不够可信。
- **错误证据**：真实媒体 API 测试首次得到 `0.817～1.200` 秒，和生成前记录的 `0.800～1.200` 秒不一致。
- **排查过程**：分别检查容器平均帧率、配置帧率和 FFmpeg `showinfo` 输出的逐帧 PTS，确认 VFR 平均值已经包含
  掉帧影响，不能作为原始采集节拍。
- **根本原因**：把掉帧后的平均帧率误当成配置要求的标称帧率，用受故障影响的指标推导故障位置。
- **解决方案**：使用配置快照中的标称帧率作为期望帧间隔，通过真实视频逐帧 PTS 的超阈值间隙定位异常窗口；
  帧数、窗口和预先记录的故障真值分别计算后再对照。
- **验证方法**：公开 API seam 真实生成 2 秒、15 FPS 视频，检测 30 帧预期中的 6 帧缺失，并返回第 1 路
  `0.800～1.200` 秒窗口及 `matched` 对照结果。
- **回归检查**：相同种子两次运行得到相同检测结果和故障真值哈希；正常场景六项视频检查全部通过。
- **经验与面试表达**：媒体元数据中的平均值和采集配置的标称值用途不同；检测异常窗口应基于原始逐帧时间证据。

## 2026-08-24：pytest tmp_path 在当前沙箱下无法复用创建的目录

- **开发阶段**：Ticket 08 测试验证。
- **问题现象**：运行 `pytest backend/tests` 时所有测试在 setup 阶段报 `PermissionError: [WinError 5]`，
  无法访问 pytest 通过 `tempfile.mkdtemp` 创建的临时目录；手动 `os.mkdir` 创建的目录却可以正常读写。
- **影响范围**：本地与 CI 均无法收集测试，Ticket 08 的新增 API 测试无法执行。
- **错误证据**：`os.scandir` 对 pytest 创建的临时目录返回拒绝访问，而同一进程手动创建的目录可列可写。
- **排查过程**：区分代码错误与环境错误，对比 `tempfile.mkdtemp`、`os.mkdir` 和 PowerShell `New-Item` 的权限结果。
- **根本原因**：当前 Windows 沙箱对 `tempfile.mkdtemp` 创建的目录设置了不可复用的访问控制，导致 pytest 内置
  `tmp_path` fixture 生成的目录同进程无法再次访问。
- **解决方案**：新增 `backend/conftest.py`，用 `os.mkdir` 在项目内 `tmp/` 目录创建函数级临时目录，
  清理失败时静默忽略沙箱限制；同步把 `tmp/` 加入 `.gitignore`。
- **验证方法**：后端完整 Pytest 47 项通过，新增 T08 存储场景测试可稳定执行。
- **回归检查**：后续在沙箱外环境仍需验证不引入权限问题；`tmp/` 目录不进入 Git。
- **经验与面试表达**：测试入口必须适应当前执行环境，环境错误要与业务断言失败分开记录。

## 2026-08-24：截断视频让掉帧检查误报空窗口

- **开发阶段**：Ticket 08 存储不足场景。
- **问题现象**：storage_exhaustion 场景的视频被提前截断后，`video_frame_drop` 检查报
  `IndexError: list index out of range`，运行记录无法完成。
- **影响范围**：新增存储场景会直接触发视频检查器对截断媒体的健壮性缺陷。
- **错误证据**：`detected_channel` 被判定为 1，但 `drop_windows` 为空，代码直接取 `[0]` 失败。
- **排查过程**：对比 video_drop 场景（VFR 产生真实间隙）与 storage_exhaustion 场景（简单截断无间隙），
  确认“帧数缺失”和“存在掉帧窗口”不是同一事实。
- **根本原因**：视频检查器假设帧数减少必然伴随可定位的掉帧窗口，未处理媒体整体提前结束的情况。
- **解决方案**：在取 `drop_windows[0]` 前增加非空判断；无窗口时只报告帧数差异，不伪造窗口。
- **验证方法**：T08 快速存储场景 3 项 storage 检查均命中故障真值；原 T06 掉帧场景窗口和真值对照保持不变。
- **回归检查**：重新运行完整后端测试 47 项通过，T06/T07 既有断言无变化。
- **经验与面试表达**：同一指标（帧数差异）可能来自不同根因，检查器要区分“缺失”和“可定位窗口”。

## 2026-08-24：MP4 容器会规范化视频时间戳导致全局偏移丢失

- **开发阶段**：Ticket 09 固定偏移时间对齐。
- **问题现象**：用 FFmpeg `setpts` 或 `-itsoffset` 给视频加上固定偏移后，`showinfo` 读出的 `pts_time` 仍然从 0 开始，跨通道偏移无法保留。
- **影响范围**：若直接把偏移写入容器时间戳，对齐模块将无法从真实媒体中估计偏移。
- **错误证据**：生成 camera_2 带 0.05 s 偏移的视频后，首帧 `pts_time` 仍为 0，与 camera_1 无区别。
- **排查过程**：分别测试 `setpts=PTS+offset/TB`、`-itsoffset`、`-output_ts_offset` 和 MKV 容器，结果均被规范化或偏移帧被丢弃。
- **根本原因**：MP4/MKV 等容器在封装时会将时间戳重新基准到首帧，不能依赖容器保存绝对偏移。
- **解决方案**：改用“共同事件锚点”表达偏移——每路视频在本地时间轴的特定帧插入白帧闪光，IMU 在对应真实时刻插入加速度冲击峰值；对齐模块通过检测最亮帧和最大 accel_x 峰值估计各通道锚点时间，再计算相对参考通道的校正量。
- **验证方法**：固定偏移场景生成四路视频和 IMU，API 契约测试验证估计校正量与故障真值误差小于 1 ms；对齐后视频残差接近 0，IMU 残差反映注入抖动。
- **回归检查**：重新运行全部后端测试 50 项通过；原有视频掉帧、IMU 异常和存储不足场景检查保持不变。
- **经验与面试表达**：当容器无法保留绝对时间戳时，可以用可检测的跨通道共同事件作为锚点，把“全局偏移”问题转化为“事件时间差”问题。

## 2026-08-24：多事件线性回归修复时钟漂移估计

- **开发阶段**：Ticket 10 线性漂移时间对齐。
- **问题现象**：容器时间戳会把各路媒体重新归一化，单个共同事件只能估计固定偏移，无法观察时钟速率差异。
- **解决方案**：新增 `linear_drift` 合成场景，在生成前记录每路偏移、漂移率和预期结果；视频和 IMU 各生成三个共同事件，
  API 对公开运行记录使用多事件线性回归估计校正截距和漂移率。
- **验证证据**：`test_linear_drift_alignment_api.py` 通过；四路视频至少识别三个共同事件，camera_4 漂移率估计约为
  `-0.03 s/s`，校正后最大残差约 11.111 ms，小于校正前 233.333 ms，并返回 `truth_comparison=matched`。
- **复盘**：视频帧量化会造成毫秒级参数误差，因此真值对照使用明确的帧量化容差；原始锚点、前置指标、回归参数、后置指标和
  残差趋势分别保存，未用校正结果覆盖原始证据。

## 2026-08-23：只看 IMU 时间戳间隔会混淆丢样与时钟异常

- **开发阶段**：Ticket 07 IMU 异常场景。
- **问题现象**：时间戳倒退后的恢复间隔也会变大；若只按相邻时间戳间隔推断丢样，会把同一个时钟异常再次统计为丢样。
- **影响范围**：丢样数量、异常位置、采样间隔分布和故障真值对照可能互相污染。
- **错误证据**：构造倒退样本时，相邻间隔同时出现负值和补偿性正间隔，单一“间隔大于阈值”规则无法区分样本缺失与时钟恢复。
- **排查过程**：把样本连续性和时间连续性拆开，分别检查 `sample_index` 序列与 `timestamp_s` 序列。
- **根本原因**：样本编号回答“数据是否缺失或重复”，时间戳回答“采样时钟是否单调和稳定”，两者不是同一事实来源。
- **解决方案**：合成 CSV/JSONL 增加稳定样本编号；丢样和重复由编号计算，倒退及间隔分布由原始时间戳计算，再分别与生成前故障真值对照。
- **验证方法**：公开 API 参数化测试覆盖 CSV/JSONL；固定种子场景各检出 1 处丢样、重复和倒退，间隔分布检出 4 个异常间隔。
- **回归检查**：两种格式的正常场景五项 IMU 检查全部通过，故障真值对照为 `not_applicable`，没有把“无故障”误写成“命中”。
- **经验与面试表达**：传感器完整性检查要区分序列身份和采样时钟，不能用一个时间差指标解释所有数据质量问题。

## 2026-08-24：锚点自动识别与内容同步评价不能共用一个结论

- **开发阶段**：Ticket 11 锚点复核与内容同步。
- **问题现象**：自动识别的闪光帧或 IMU 冲击峰值可能因帧量化、阈值或异常事件而偏移；如果只展示校正后的时间差，测试工程师无法知道哪些锚点被使用，也可能把时间接近误写成画面内容同步。
- **影响范围**：时间对齐参数、复核后的残差、跨模态同步结论和后续报告证据会互相混淆。
- **错误证据**：API 测试先保存自动锚点与所有产物 SHA-256，再提交 camera_4 锚点人工调整；复核返回 revision 1、参数发生变化，而产物哈希保持一致；内容同步仍按视频闪光与 IMU 峰值事件序号独立返回通过。
- **排查过程**：沿用 Ticket 09/10 的公开运行记录 seam，检查视频白帧与 IMU 峰值的检测结果、稳定锚点 ID、排除后的共同事件数量，以及前端提交的复核请求。
- **根本原因**：时间戳是事件发生位置的数值证据，内容同步是事件身份和顺序的另一项证据，两者回答不同问题。
- **解决方案**：新增带 `channel:event-N` 稳定引用的锚点明细；复核只替换独立对齐分析快照并增加 revision，原始产物和检测结果不变；内容同步按事件序号统计视频闪光和 IMU 冲击峰值的对应关系，并对缺失/不一致返回可理解的失败或降级状态。
- **验证方法**：后端完整 Pytest 54 项通过；前端完整 Vitest 19 项通过；TypeScript、Ruff、Prettier、Vite 生产构建和 `git diff --check` 通过。
- **回归检查**：Ticket 09 固定偏移和 Ticket 10 线性漂移定向测试保持通过；排除过多共同锚点返回 422，不生成不完整的对齐结果。
- **经验与面试表达**：可复核的测试证据必须同时保留“机器看到了什么”“人调整了什么”和“另一类同步证据是否成立”，不能用一个漂亮的残差数字替代事实链。

## 2026-08-24：判定模式和阈值来源必须跟随运行快照

- **开发阶段**：Ticket 12 三种判定模式。
- **问题现象**：同一份检测结果在正式规格、工程目标和版本基线语境下含义不同；如果只保存一个通过/失败字段，历史运行会被后续阈值配置误解。
- **根本原因**：判定语义、阈值来源和运行时配置没有作为同一份不可变快照保存，且摸底分析不应被压缩成合格性结论。
- **解决方案**：新增判定配置和运行判定结果；快照记录三种阈值来源的判定优先级。需求验收允许合格/不合格，工程目标明确不代表产品承诺，摸底分析固定返回 `not_applicable` 并只展示分布与趋势。阈值名称、数值和整数边界由后端白名单校验，AI 没有修改入口。
- **验证方法**：API 主 seam 覆盖三种模式、阈值来源、运行快照和非法输入；前端覆盖工程目标模式及阈值来源提交。
- **验证证据**：Ticket 12 定向 API 9 项通过，另有 v7→v8 迁移测试；全量后端 64 项、前端完整 Vitest 22 项、TypeScript、Ruff、Prettier 和 Vite 生产构建通过。
- **经验与面试表达**：验收结论不是检测事实本身，报告必须同时说明“用什么语义、什么来源、什么阈值”得出结论；摸底数据只能支持趋势观察。

## 2026-08-24：组合故障的关联窗口不能替代根因结论

- **开发阶段**：Ticket 13 温升关联组合故障场景。
- **问题现象**：只分别展示视频掉帧、IMU 丢样、温度和日志，会让审查者无法确认这些证据是否发生在同一时间窗口；直接把它们同时出现又会把相关性误写成温度导致的根因证明。
- **排查过程**：沿用 Ticket 06、07 的公开运行记录 API seam，先在生成前写入温升、掉帧、丢样的窗口和预期检查，再分别从真实视频 PTS、IMU 样本编号/时间戳、设备状态 CSV 和设备日志计算结果。
- **根本原因**：不同证据源的时间字段和检测语义不同，不能使用故障真值回填检测指标，也不能用一个检查结果代替跨证据审查。
- **解决方案**：新增 `temperature_combination` 场景；快速 2 秒、15 FPS、50 Hz、固定种子 42 的运行在 `0.800～1.200` 秒窗口注入视频掉帧和 IMU 丢样，设备状态生成 40～72 °C 温升趋势，日志记录同期事件；检测结果保存稳定 `fault_truth`、`device_status` 和 `device_log` 引用，并明确消息只表示时间相关性。
- **验证方法**：组合场景 API 契约测试验证 2 次运行的检测结果、故障真值哈希和窗口稳定；视频掉帧、IMU 丢样/间隔、温度资源和日志关联预期检查均为 `failed` 且 `truth_comparison=matched`，正常场景无新增组合故障检查。
- **回归检查**：后端完整 Pytest 66 项、前端 Vitest 22 项、TypeScript、Ruff、Prettier 和 Vite 生产构建通过；前端旧运行记录缺少证据引用字段时按空列表兼容。
- **经验与面试表达**：跨证据分析先回答“是否同窗发生、各自看到了什么”，再由人工或后续诊断提出可能原因；确定性检查本身不宣称根因。
