# AI 智能硬件测试执行与诊断平台：面试案例

本文是持续维护的面试方案。开发过程中只记录真实完成的能力，计划功能必须明确标注。

## 一句话介绍

面向多传感器采集设备的本地测试平台，通过合成视频、IMU、设备状态和日志复现 POC/EVT 阶段的数据质量问题，使用确定性规则完成检测，再由大模型基于可引用证据辅助诊断和生成报告。

## 求职定位

主要面向 Python 自动化测试工程师岗位，同时展示智能硬件或嵌入式测试经验。

## 项目来源与合规边界

项目灵感来自个人在多传感器采集设备测试中的通用经验，但采用洁净重写：不复制原公司的代码、Prompt、数据、文档、界面、名称、接口或未公开产品信息。项目使用虚构设备、公开格式和带故障真值的合成数据。

## 要解决的问题

- 没有真实设备时，如何稳定复现视频、IMU、资源和日志异常。
- 如何区分原始时间戳差异、对齐处理效果和最终验收结论。
- 如何让自动化检查提供稳定事实，同时让 AI 发挥归纳和辅助诊断价值。
- 如何把自动化结果与人工检查结果统一汇总，但不覆盖原始状态。
- 如何在模型 API 不可用时仍完成测试和报告。

## 首版范围

- 四路合成视频、一路合成 IMU、设备状态和日志。
- 六个场景：正常、单路掉帧、多路同步漂移、IMU 异常、存储不足、温升关联组合故障。
- 固定偏移校正和线性漂移校正。
- 正式规格、工程目标、版本基线三种判定模式。
- 人工结果录入及 CSV/Excel 导入。
- 硅基流动 AI 诊断与 Mock 模式。
- 应用内报告、独立 HTML、ZIP 证据包和 Allure。

## 技术路线

- 后端：Python、FastAPI、Pytest、SQLite。
- 前端：React、TypeScript。
- 数据生成与分析：FFmpeg、ffprobe、Python 数值生成器。
- AI：硅基流动为默认服务，通过独立适配层调用。
- 持续集成：GitHub Actions，默认使用 Mock 模式。

- 采集任务配置与查看能力保持独立；首个运行记录能力见下一节，完整队列和状态机仍未实现。

## 已验证的首个端到端运行（2026-08-22）

- 执行快速正常采集任务会创建独立运行记录并保存配置快照；重复执行得到不同 ID，历史记录可重新读取。
- 运行记录保留排队、生成数据、执行检查、汇总结果和已完成五个阶段事件。
- 真实 HTTP 冒烟生成一路 2 秒、640×360、15 FPS 的 H.264 MP4（134611 字节），以及 IMU CSV（3336
  字节）、设备状态 CSV（151 字节）、设备日志（95 字节）和预定空故障真值 JSON（113 字节）。
- 产物均标记为实际生成；必需文件、H.264 元数据和正常场景三个基础检查通过，没有基础误报。
- 运行详情页面可展示完成状态、阶段、产物清单和基础检查；本地 Pytest 7 项、Vitest 5 项及完整工程检查通过。
- 首个运行切片当时使用同步执行；后台队列、取消和异常中断现已在下一节完成验证，更多通道仍属后续 ticket。

## 已验证的运行管理能力（2026-08-22）

- 后台执行器使用单工作线程按提交顺序消费运行记录；后续运行先以排队状态返回，避免本机并发生成争抢资源。
- 排队或执行中的运行可通过公开 API 取消；取消立即成为终态，当前生成步骤安全收尾后保留已产生证据。
- 重新执行从原运行的配置快照创建新记录和新 ID，原运行仍可通过详情 API 读取且内容不被覆盖。
- 应用启动会把上次进程留下的排队或执行中记录标为异常中断，并记录恢复事件和可理解的错误原因。
- 运行详情页面轮询公开 API 展示状态，并按终态提供取消或重新执行操作；自动化验证结果见 Ticket 05 证据。

## 已验证的可配置多通道生成（2026-08-22）

- 页面和 API 支持快速、标准、自定义三种模式；自定义参数覆盖 2～300 秒、1～4 路视频、三种分辨率、
  五种帧率、MP4/MKV、CSV/JSONL、四种 IMU 采样率及可配置随机种子，视频编码固定 H.264。
- API seam 真实生成双路 2 秒 640×360、15 FPS 的 H.264 MKV 和 100 Hz JSONL IMU，并同步生成设备状态、
  设备日志及故障真值；相同种子两次运行的全部产物 SHA-256 与重复性指纹一致。
- 300 秒长稳请求只真实生成 5 秒媒体，设备状态保留完整虚拟时间趋势；运行详情明确展示实际生成、
  虚拟时间模拟、请求/真实时长、产物哈希和重复性指纹，避免把模拟趋势描述成真实录制。
- 前端和 API 使用相同的 6 亿像素帧安全上限，四路 1080p、60 FPS 超限组合在任务入队前被拒绝。
- 本地 Pytest 29 项、Vitest 8 项、Ruff、TypeScript 和 Prettier 检查通过。故障注入、后台队列和完整检查器
  仍由后续 ticket 实现，不在本次能力声明中。

## 已验证的人工检查结果（2026-08-22）

- 测试工程师可在运行详情新增和修改人工检查项，准确区分通过、失败、阻塞和未执行状态。
- 实际结果、备注、执行时间及 TXT、PNG、JPEG、PDF 小型附件独立保存；附件限制为 1 MiB，API 只返回安全元数据。
- CSV 与 XLSX 使用统一五列表头和同一套行校验；无效批次返回行号与字段，SQLite 事务避免部分静默写入。
- 运行详情分别保留自动化 `checks` 与人工 `manual_check_results`，页面统一展示但不会互相覆盖。
- API 测试覆盖新增、修改、附件、CSV/XLSX 和错误原子性；UI 测试覆盖新增、修改和可定位导入错误。
- rebase 到已含 Ticket 05 的最新 `main` 后，完整验证为后端 Pytest 37 项、前端 Vitest 12 项，
  TypeScript、Ruff、Prettier 和 Vite 构建通过。

## 已验证的单路视频掉帧检测（2026-08-23）

- 页面可创建固定种子的单路视频掉帧场景，并通过既有运行记录生命周期执行，不引入独立旁路。
- 生成器在媒体生成前记录目标通道、`0.800～1.200` 秒注入窗口、6 帧缺失和预期检测结果；同一任务重复
  运行得到相同检测结果及故障真值 SHA-256。
- 视频检查通过真实媒体验证路数、H.264 编码、帧率、时长、掉帧和坏帧，并以统一结果返回指标、异常窗口
  和故障真值对照；快速场景从预期 30 帧中检测到第 1 路实际 24 帧，故障真值对照为命中。
- 异常窗口来自 FFmpeg 逐帧 PTS 间隙，不由故障真值直接回填；运行详情展示失败指标、窗口和对照结果。
- 正常场景新增的六项视频检查全部通过，无新增误报。后端完整 Pytest 35 项、前端 Vitest 11 项通过；
  视频以外的 IMU、资源和日志确定性检查仍由后续 ticket 实现。

## 已验证的 IMU 异常检测（2026-08-23）

- 页面可创建固定种子的 IMU 异常场景，并通过公开 API 运行记录生命周期完成生成和确定性检查。
- 生成器在写文件前记录丢样、重复和时间戳倒退的样本位置、预期检查及失败状态；同一配置重复运行得到相同
  IMU、故障真值 SHA-256 和统一检测结果。
- 检查器从真实 CSV/JSONL 产物分别计算采样率、样本编号缺口、重复编号、时间戳倒退，以及最小、最大、
  平均、P95 和异常间隔数量，不从故障真值回填检测值。
- 快速 50 Hz 场景各检出 1 处丢样、重复和倒退，间隔分布包含 4 个异常；三类预定故障均与真值位置命中。
- CSV 与 JSONL 参数化契约均通过；两种格式的正常场景五项 IMU 检查全部通过，没有新增误报。运行详情可展示
  每类异常消息、样本位置、间隔指标及故障真值对照。
- 本轮完整验证为后端 Pytest 45 项、前端 Vitest 16 项，并通过 Ruff、TypeScript、Prettier、Vite 生产构建
  和仓库安全扫描；这些数量只记录 2026-08-23 本地实际运行结果。

## 已验证的存储不足与提前停止检测（2026-08-24）

- 页面可创建固定种子的存储不足场景；生成器在写文件前记录存储阈值 500 MB、提前停止位置和预期检查项。
- 系统通过缩短真实媒体时长模拟提前停止，device_status.csv 用可控虚拟趋势展示存储下降到阈值以下，
  device.log 记录存储警告和录制提前结束事件，不消耗不可控的真实磁盘空间。
- 检查器从视频实际时长、设备状态存储指标和日志事件三个维度输出统一结果：
  `storage_premature_stop`、`storage_exhaustion`、`storage_log_correlation`。
- 快速 2 秒场景真实生成 1 秒媒体，三项检查均失败且与故障真值对照为命中；同一任务重复运行得到相同
  故障真值 SHA-256 和相同检测结果。
- 正常场景的 storage 检查全部通过且 `truth_comparison` 为 `not_applicable`，没有新增误报。
- 本轮后端完整 Pytest 47 项通过，Ruff 和仓库安全扫描通过；前端 TypeScript 与 Prettier 检查通过。
  前端 Vitest 与 Vite 生产构建在当前 Windows 沙箱下因 `spawn EPERM` 无法执行，已记录为环境限制而非代码缺陷。

## 核心链路

```text
配置采集任务
  → 生成带故障真值的合成数据
  → 执行确定性检查
  → 分析对齐前指标
  → 执行时间对齐
  → 分析对齐后残差
  → 汇总人工结果
  → 构建诊断证据包
  → AI 结构化诊断
  → 对照故障真值评估诊断
  → 导出报告与证据包
```

## AI 的职责边界

AI 负责归纳异常、提出可能原因、引用证据、说明不确定性并给出复测建议。AI 不控制设备、不修改原始证据、不决定确定性指标，也不能自行发明验收阈值。

4. 展示确定性检查发现的掉帧和丢样事实。
5. 展示 AI 如何引用同期温度、日志和失败指标提出原因与复测建议。
6. 对照故障真值展示命中、漏判和无证据推测。
7. 关闭模型或切换 Mock，证明测试主流程仍可完成。
8. 导出 HTML 和 ZIP 证据包。

## 首版验收标准

- 六个内置场景均可从界面运行。
- 支持快速、标准和自定义数据配置。
- 真实生成短视频、IMU、状态指标和日志。
- 两种时间对齐方法均可执行，并保留对齐前后结果。
- 正常场景不误报，五个故障场景的预期检查均可识别。
- 三种阈值来源产生符合定义的结论。
- 人工结果和自动化结果分别保存并统一展示。
- AI 输出通过 Schema 和证据引用校验，并可对照故障真值评估。
- 模型不可用时仍能完成测试和原始报告。
- HTML、ZIP、Allure 和 CI 产物可验证。
- README 支持面试官在 Mock 模式下复现。
- 仓库不包含原公司资产或敏感信息。
