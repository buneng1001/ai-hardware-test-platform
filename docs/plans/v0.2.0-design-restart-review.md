## 2. 已确认的 v0.2.0 设计共识

### 2.1 产品和版本

```text
项目
└── 产品版本
    ├── 原始测试用例
    ├── 自动化测试用例
    ├── 测试数据资产
    ├── 测试组
    └── 测试记录与最终报告
```

- 项目是产品的长期工作容器。
- 产品版本用于区分 Beta 产品的不同版本。
- v0.2.0 不要求用户在项目刚创建时填写准确的测试范围、核心范围或阶段目标。
- 测试范围随着用户导入用例、编辑用例和建立测试组逐步形成。
- v0.2.0 暂不建立独立的测试需求对象；导入的需求资料先整理为原始测试用例。
- 导入文件中的“软件版本”保留为原始字段，并在加入测试组时与当前产品版本校验。

### 2.2 原始测试用例和自动化测试用例

用户常用的原始用例字段为：

`用例编号、测试用例标题、优先级、预置条件、输入、操作步骤、预期结果、测试类型、模块、测试项、测试结果、测试记录、测试前备注信息、计划执行时间、附件、软件版本`

- 原始测试用例表保持用户导入内容，不被自动化转换覆盖。
- 导入时先核对字段映射，再询问是否导入历史结果、测试记录、测试前备注、计划执行时间和附件。
- 导入的历史结果不覆盖本次新测试结果。
- 同一份文件再次导入时保留为新的导入记录，不自动覆盖旧数据。
- 原始用例编号只要求在同一导入记录中唯一；平台内部使用“导入记录 + 原始用例编号”定位来源。
- 自动化用例由系统生成新的唯一编号，编号不可修改、不复用。
- 自动化用例表只显示一列来源用例编号，该编号可点击跳转到原始用例。
- 自动化用例的来源详情可查看原始文件、导入记录和转换记录，但不在主表重复堆叠多列。
- 用户可以编辑标题、输入、步骤和预期结果，也可以新增、删除和勾选自动化用例。
- 新增自动化用例必须填写来源用例编号。
- 自动化用例初次生成后直接进入可编辑表格；用户修改后必须点击“校验”。
- AI 修改意见使用独立输入框；一次提交所有已修改或有反馈的行，提交后反馈输入框清空。
- AI 转换失败或低可信度内容直接在同一张表中用行背景色和简短备注提示，不增加复杂的分析模块。
- AI 服务不可用时允许使用低可信度规则转换，但必须提示用户人工审核。

### 2.3 测试组

- 测试组属于某个项目的某个产品版本。
- 测试组代表一次用户定义的测试范围，可以包含多个模块。
- 测试组中的成员可以是人工用例、自动化用例或同时包含两者。
- v0.2.0 不设置“必测/可选”作为强制执行模型；不需要的用例直接从测试组移除。
- 新建测试组只填写名称、项目/产品版本和当前已勾选项目。
- 完整编辑统一放在测试组详情页。
- 测试组详情可以添加、删除、排序用例，管理数据包关联，进入人工测试和执行自动化测试。
- 测试组列表支持搜索、排序、分页、隐藏和删除。
- 隐藏只影响列表展示，可以恢复显示；删除需要确认影响范围。
- 删除测试组会删除关联的在线报告、自动化执行记录和人工记录，但不自动删除平台级数据包。

原始用例表和自动化用例表中的“加入测试组”是选择入口，不是立即执行：

- 用户勾选的项目保存为项目/版本范围内的待加入清单；关闭网站后再次打开仍保留。
- 没有测试组时，点击“加入测试组”可以打开新建测试组弹窗并带入已勾选项目。
- 有测试组时，用户可以搜索并选择目标测试组。
- 成功加入后，待加入清单默认清空。

### 2.4 测试数据和数据任务

v0.1.0 的采集任务是数据生成/导入任务，不是设备控制任务，也不等同于自动化测试任务。

- 用户可以执行采集任务生成数据，也可以导入数据。
- 采集任务可以不立即执行；已有生成结果可以直接作为自动化测试输入。
- 测试数据页面负责执行和管理这些数据任务，并查看数据包实际情况。
- 数据包需要展示平台标准格式检查、文件和通道情况、时间戳、完整性，以及正常数据或故障数据属性。
- 测试组中不允许直接上传未经校验的文件。
- 测试组只能选择平台中已经生成并校验、或导入并校验的数据包。
- 数据包可以被多个测试组和多个自动化用例使用。
- 数据包和自动化用例是多对多关系；取消一条关联不影响其他用例和测试组。
- 同一测试组可以给不同用例分配不同数据包，也可以批量关联后逐条调整。
- 数据包更新时提示“输入源数据包有更新”，默认推荐最新结果，但不自动替换已有关系。
- 生成新数据包产生新的版本/指纹，不覆盖旧数据包，旧包可用于复现。
- 数据包删除需要显示影响范围；可以解除关联、删除数据包以及按用户选择清理依赖记录。

数据检查分两类：

1. 执行前校验：检查数据包存在、格式合规、能够被执行；失败时阻止自动化测试启动。
2. 用例内数据检查：验证视频、IMU、时间戳、内容和故障场景是否符合该用例预期；失败时记为用例“失败”，但不阻止生成最终报告。

### 2.5 自动化执行和重试

- 执行模式在测试组详情点击“执行自动化测试”时选择，不绑定到用例或测试组。
- v0.2.0 只启用“数据驱动模拟”。
- “模拟设备执行”放到 v0.4.0；“连接被测设备”放到后续版本。
- 执行前检查失败时，用户修复测试组或替换数据包后，在同一准备流程点击“重新检查”。
- 执行前检查失败不创建正式自动化执行记录。
- 自动化执行真正开始后生成不可覆盖的执行快照和正式执行记录。
- 执行开始后的失败、取消或中断，再次执行都创建新的执行记录和新的快照。
- 已完成部分的中断记录保留，状态为“已中断”。
- 所有计划的用例/数据组合都尝试完成后，执行记录可以是“已完成”，即使其中有失败。
- 环境或数据导致无法完成执行时为“阻塞”；预期结果不满足时为“失败”。

结果状态及界面显示：

| 内部状态 | 界面/报告显示 | 含义 |
| --- | --- | --- |
| `passed` | 通过 | 实际结果符合预期 |
| `failed` | 失败 | 已执行但实际结果不符合预期 |
| `blocked` | 阻塞 | 因环境、连接或数据原因无法完成 |
| `not_run` | 未执行 | 本次没有开始执行 |

### 2.6 人工测试结果

- 人工测试使用独立页面，不混入自动化执行页面，也不在报告页面填写。
- 用户选择项目、产品版本和测试组后，逐条填写人工结果。
- 用户可以分多次保存草稿，不要求一次填完整组。
- 人工页面只显示人工用例和混合用例，纯自动化用例不显示。
- 未填写的人工用例在最终报告中显示“未执行”。
- 人工测试结果可以修改、删除和重新用于生成报告。
- 人工记录可以关联附件；附件规则、使用情况和清理入口需要让用户明确可见。
- 删除人工记录时删除关联附件，已有在线报告标记为过期。

### 2.7 最终报告

- 最终报告由用户选择一条自动化执行记录和一条或多条人工测试记录生成。
- 允许只有自动化记录或只有人工记录，缺少另一部分显示“未执行”或“没有对应人工/自动化用例”。
- 报告只合并同一测试组、同一产品版本的记录。
- 自动化和人工结果不一致时保留两者，标记“结果不一致”，交给 AI 分析。
- 报告失败不阻止事实结果生成。
- AI 分析失败时显示分析未完成，允许单独重试。
- 报告页面提供 HTML 和纯文字下载。
- 重新生成会覆盖平台当前在线报告，不影响用户已经下载到本地的文件。
- 执行记录、人工记录、测试组配置或数据包关联变化后，当前在线报告标记为过期，不自动改写。
- 删除在线报告不删除底层测试记录和数据包。
- 报告只保留必要支撑数据，不默认生成证据包、哈希码和大量原始日志。
- 运行日志只保留影响判断的关键问题；详细日志按需查看或下载。

报告顺序：

1. 测试基本信息；
2. 阶段推进评估；
3. AI 分析；
4. 测试范围总览；
5. 按模块展示的详细结果；
6. 跨模块问题、补充验证和回归建议。

每个模块最开始突出显示“当前结论”，然后展示实际支撑数据、自动化/人工结果、关键失败和异常。

阶段推进评估只是建议，不是强制准入开关。AI 可以建议“进入下一阶段”“有条件进入”或“暂缓并补充验证”，但最终由公司根据实际情况决定。

### 2.8 趋势和版本对比

- 趋势图放在项目详情页，不放首页。
- 默认展示整个项目的历史趋势，可按产品版本、模块、测试组或测试用例筛选。
- 只统计已经生成最终报告的结果。
- 展示自动化/人工通过、失败、阻塞、未执行数量和模块结果变化。
- 没有数据时显示“暂无趋势数据”；筛选无结果时显示“当前筛选条件暂无数据”。
- 只有一份报告时显示一个数据点。
- 在线报告删除后对应数据点移除；报告过期后保留并标记。
- 版本对比由用户主动选择两个产品版本或两份最终报告。
- 不自动假设最新版本一定和上一版本比较，避免测试范围不一致。

- Beta 产品需求/测试用例资料导入；

- AI 辅助用例转换、用户编辑、反馈提交和校验；
- 无 AI 时的低可信度规则转换；
- 数据生成/导入任务执行与数据包管理；

- 测试组创建、编辑、隐藏、删除和历史记录管理；
- 数据驱动模拟自动化测试执行；
- 执行前检查、具体错误反馈和有限重试；
- 独立人工测试结果页面；
- 模块化 HTML/纯文字最终报告；
- 项目趋势和用户主动版本对比；

## 4. 旧分支与最新 main 的冲突

旧分支：`codex/v0.2.0-report-and-governance`

说明：旧分支的 `CONTEXT.md` 来自信息不足的 Grill，只作为历史草稿，不作为 v0.2.0 设计依据。

### 冲突一：设备执行能力提前

旧稿把设备控制、设备能力和自动化测试执行放进 v0.2.0。最新设计确认：v0.2.0 只做数据驱动模拟，模拟设备执行放到 v0.4.0，真实设备放到更后版本。

### 冲突二：采集任务含义错误

旧稿将采集任务视为每次测试都要执行的设备采集流程。最新设计确认：采集任务主要负责生成/导入和检查数据，用户可以直接选择已有生成结果作为自动化测试输入。

### 冲突三：自动化任务的版本边界错误

旧稿把测试用例到自动化任务的完整推荐和执行模型作为 v0.2.0 基础。最新设计确认：v0.2.0 包含 AI 辅助转换为可编辑自动化用例，这是本平台的重要价值；更深入的需求分析、范围识别和回归推荐放到 v0.3.0。

### 冲突四：测试运行的概念混淆

旧稿将“测试运行”作为核心领域对象。最新设计区分：

- “执行自动化测试”是页面按钮/动作；
- “自动化测试执行记录”是一次正式执行后的不可覆盖快照记录；
- v0.1.0 的“运行记录”是数据生成/导入/检查运行记录，不能直接等同于 v0.2.0 自动化执行记录。

### 冲突五：准入被设计为强制质量门禁

旧稿要求失败检查触发准入失败并阻断后续流程。最新设计确认：最终报告不因失败或人工缺失而阻塞；“阶段推进评估”只提供建议，不替公司做最终阶段决定。

### 冲突六：人工结果和报告关系错误

旧稿倾向于把人工复核嵌入自动化运行或报告流程。最新设计确认：人工测试结果使用独立页面录入，最终报告页面只选择记录并汇总。

### 冲突七：报告和证据包过度设计

旧稿强调哈希、证据包和大量日志关联。最新设计确认：v0.2.0 最终报告优先提供 HTML、纯文字、模块结论和必要支撑数据；详细日志和附件按需使用，用户可以清理。

### 冲突八：强制保留和归档倾向

旧稿倾向保留或归档所有测试资产。最新设计确认：测试组、执行记录、报告、数据包和转换记录都应允许用户在看到影响范围后删除。

- [ ] 可以创建项目和产品版本。
- [ ] 可以导入用户约定字段的原始测试用例。
- [ ] 导入前可以确认字段映射和可选历史字段。
- [ ] 可以按模块、测试项、优先级和软件版本筛选。
- [ ] 导入后默认只勾选一条示例用例，用户可以全选或取消。
- [ ] 关闭网站后重新打开，待加入测试组清单仍存在。
- [ ] 可以生成自动化用例表并保持原始用例不变。
- [ ] 自动化用例编号唯一、不可编辑、不复用。
- [ ] 来源用例编号可以点击回原始用例。
- [ ] 用户可以编辑、新增、删除和勾选自动化用例。
- [ ] 修改或新增后未校验时，不能加入测试组或执行。
- [ ] AI 反馈可以批量提交，提交后反馈输入框清空。
- [ ] AI 失败或低可信度行在表格中有明显颜色和简短备注。

### 5.2 数据和测试组

- [ ] 可以执行 v0.1.0 数据生成/导入任务并查看任务历史。
- [ ] 可以查看数据包标准格式校验和实际数据情况。
- [ ] 可以区分正常数据和故障数据。
- [ ] 测试组不能直接使用未校验数据包。
- [ ] 数据包可以关联多个用例和测试组。
- [ ] 可以批量关联数据包，也可以单条调整。
- [ ] 数据源更新时有明确提示，不自动替换旧关联。
- [ ] 可以创建、编辑、隐藏、显示和删除测试组。
- [ ] 测试组详情可以管理原始用例、自动化用例和数据包。

### 5.3 自动化执行和人工结果

- [ ] 只有测试组详情中的“执行自动化测试”能启动自动化执行。
- [ ] v0.2.0 只提供数据驱动模拟模式。
- [ ] 执行前检查失败能返回错误编码、失败对象、实际值、期望值和修复建议。
- [ ] 执行前检查失败不会创建正式执行记录。
- [ ] 执行开始后生成不可覆盖快照。
- [ ] 失败、取消、中断后的再次执行生成新记录。
- [ ] 通过、失败、阻塞、未执行含义正确且中英文展示一致。
- [ ] 人工测试页面可以按测试组逐条保存结果。
- [ ] 人工缺失时最终报告显示未执行，不阻塞报告生成。
- [ ] 人工结果可以修改、删除并导致在线报告过期。

### 5.4 报告、趋势和 CI

- [ ] 可以选择一条自动化记录和多条人工记录生成最终报告。
- [ ] 只有自动化或只有人工记录时也能生成报告。
- [ ] 报告按既定顺序生成，每个模块开头突出当前结论。
- [ ] 模块结论有实际结果和支撑数据，不编造指标。
- [ ] 报告包含自动化结果、人工结果、AI 分析和回归建议。
- [ ] AI 分析失败不阻塞事实报告。
- [ ] 可以下载 HTML 和纯文字报告。
- [ ] 报告重新生成会覆盖当前在线报告，但不影响本地下载文件。
- [ ] 项目详情可以查看趋势并按版本、模块、测试组和用例筛选。
- [ ] 可以主动选择两个版本或报告进行对比。
- [ ] GitHub Actions 可以用固定样例验收上述平台流程。
- [ ] CI 不连接真实设备，不执行客户产品测试，不根据客户失败结果阻断仓库。
