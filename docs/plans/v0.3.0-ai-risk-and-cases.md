# v0.3.0 AI 测试需求分析、风险识别与用例推荐

> 状态：v0.2.0 已完成并结项，结项提交 `bd8ce13` 已推送 `main`；v0.3.0 已确认主要需求裁决，进入 To Spec 与任务拆分准备，尚未启动实现。代码基线 `0286708`。每个开发项必须能够独立人工验收，开工时核对最新 main。

## 目标

让 AI 从运行后的诊断扩展到测试前的需求分析，帮助用户判断哪些内容适合自动化，并推荐可执行测试用例。

## 功能模块

- 手动输入或粘贴测试需求、产品版本变更说明；结合项目级产品画像与已有测试记录进行结构化分析。需求文件导入/解析不在本版实现。
- AI 识别高风险功能、数据链路和潜在故障模式。
- 分析可自动化执行的步骤与需要人工确认的步骤。
- 根据风险、历史失败、覆盖情况和设备能力推荐测试用例。
- 生成推荐理由、优先级、前置条件、依赖数据和预期证据。
- 用户审核、修改和确认推荐结果。
- 将确认后的用例转换为自动化任务或测试组。
- 根据测试结果生成回归测试建议。

## 开发边界与流程

项目默认产品画像 + 手动需求文本/版本变更说明 → 结构化需求点及人工确认 → 风险分析及人工确认 → 推荐用例及人工确认 → 正式用例/自动化候选/测试组 → 数据驱动执行与报告 → 回归建议。

- 复用现有 v0.2.0 数据、组件、AI 配置和用例转换链路；不另建一套业务工作区。
- 原始用例保持人工语义；自动化候选是独立副本，必须经过既有校验与执行预检。
- 真实执行器（本地框架、Jenkins、GitHub Actions）、`cases.json` / `results.json` 文件契约及真实结果回收仍属 v0.4.0；音频与多模态仍属 v0.5.0。
- P0 01–07、11 先完成；P1 08–10 同样属于本版交付范围，在核心链路通过后实施。先收敛数据契约、审核流程及安全边界，再进入 To Spec 和 Issue 拆分。
- 需求文件导入、自动解析、格式兼容与附件解析全部延后至 v0.4.0 之后的未来版本（具体版本待定）；不改变 v0.4.0 执行器与 v0.5.0 音频/多模态已规划范围。现有 v0.2.0 正式测试用例表的 CSV/XLSX 导入继续正常工作，不得误禁。

## 安全边界

- AI 不能直接执行用例。
- AI 不能修改确定性阈值、原始数据或正式准入结论。
- 无证据支持的推荐必须标记为推测。
- AI 失败时，用户仍可手动配置和执行测试。

## 验收标准

- 同一份需求输入能够得到结构稳定、可解释的推荐结果。
- 用户可以拒绝、修改或确认每条推荐。
- 已确认推荐可以生成自动化任务。
- 回归建议可以进入下一次测试组，而不是只停留在报告文本中。
- 全局 AI 关闭时不调用真实模型，人工流程可继续；打开且配置可用时统一使用已选服务商和模型。
- 产品画像可在已有项目编辑，并可追溯到推荐输入；推荐不覆盖历史用例及正式测试事实。
- P0 闭环通过后再推进 P1；失败、取消、重试、缺失信息与无 AI 场景均需可验证。

## 单项人工验收约束（已确认）

- 每项独立定义入口、前置条件、固定样例、操作步骤、预期结果、错误/空状态、刷新与持久化结果、验收证据、回归范围；必须在本机真实运行的页面中验收，自动化测试不能替代人工确认。
- 允许依赖已验收的上游能力；未完成下游不阻碍当前项验收。必要时用固定样例或 Mock 接口验证，明确标记模拟证据；真实模型联调单独记录。
- 每项完成后用户确认，再推进后续依赖项。失败不标通过；不为了通过验收扩大范围或修改已冻结的 C 方案 UI。
- 09 与 10 分别验收，11 单独验收；其他稳定性问题逐条复现、逐条建立修复任务，不将多个独立功能塞进一个 Issue。

## 已确认需求裁决

| 问题 | 用户确认的规则 |
| --- | --- |
| 1. AI 开关 | 顶栏增加一个按钮，直接开启/关闭 AI，不必返回首页。全局关闭时规则转换、人工用例、确定性测试与事实报告继续可用。 |
| 2. 产品画像 | 项目级默认画像；不建立产品版本级结构化覆盖。新版本新增能力通过需求区补充一句或多句文字描述，AI 同时读取项目画像和本次变更说明。已保存的分析/报告历史快照不随画像修改而被改写。 |
| 3. 需求导入 | 本版不实现需求文件上传、读取、解析及格式适配；延至 v0.4.0 之后的未来开发计划。当前以手动文字输入作为 AI 分析入口。 |
| 4. 风险分析 | 保留需求、风险、用例三个审核环节；结合手动需求文本运行，不依赖未来文件导入。具体审核组件与展示方式在 To Spec 确认。 |
| 5. 对象关系 | 推荐仅为候选；审核确认后进入正式原始用例表（人工）；自动化候选另行转换/校验。推荐重复时提示关联已有用例或由用户确认更新，不自动覆盖。 |
| 6. 版本管理 | 修改需求或产品画像后旧分析标记“输入已更新”；重新生成新批次，保留历史，不自动删除旧结果，不覆盖已确认的正式用例。 |
| 7. 验收范围 | 每项独立人工验收；AI 功能区分固定样例/Mock 的功能验收和真实模型效果验收；P1 08–10 也属于 v0.3.0 交付范围。 |

说明：问题 3、4 的回复重点是推迟文件导入；据此保留手动输入后的需求/风险审核链路，不将整个 AI 需求与风险分析推迟。风险等级、字段定义等实现细节尚未冻结。

## 未开发入口的 UI 规则（用户确认）

- 保留现有 C 方案设计与“导入需求点”等待实现的入口，按钮正常呈现、可点击，不用灰色 disabled、永久“未启用”、开发中标签或页面解释段落。
- 点击尚未实现的需求导入/文件解析动作时，仅弹出统一提示“该功能开发中”，关闭后停留原页面。不得打开文件选择器、发起上传或模型请求、创建数据、跳转或模拟成功。
- 删除现有需求区常驻“需求点解析尚未接入”“本轮只提供界面”等开发进度说明，以及相关禁用提示；不影响真实可用的测试用例导入、正常字段说明、运行错误提示及必要安全提示。
- 同类未开发入口统一采用点击时提示，不影响正常可用功能的反馈。验收时分别检查页面静态外观与点击行为；真实可用功能必须仍可操作。

## To Spec 前仍需细化的事项

- 01：全局开关的存储及作用域、配置失效/真实模型不可用时的状态、运行中关闭 AI 的处理。
- 02–04：画像必填项、需求文本保存及编号、需求/风险审核状态、风险级别与证据来源、缺少阈值时的处理。
- 05–07：候选去重键、关联/更新授权、批量审核及正式用例发布的幂等规则；历史批次与输入指纹。
- 08–11：回归输入范围、附件继承策略、关联提示位置、预留入口清单和统一弹窗行为。
- 固定样例与真实模型测试材料、单项验收文档、每项实际 UI 设计及 API/数据契约，在对应 Ticket 实现前确认；不重新开启已确认的版本范围和业务语义。
