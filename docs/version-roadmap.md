# 版本路线图

本文描述“智能硬件自动化方案管理平台”的预计演进路线。版本目标是规划内容，不能替代代码、测试或验收证据；只有已经产生可复查证据的能力，才能在面试材料中描述为已完成。

用户操作流程见 [用户视角使用流程与版本对应关系](user-flow-roadmap.md)，讨论形成的统一设计结论见 [平台设计结论](platform-design-conclusions.md)。

各版本的独立开发计划见：

- [v0.1.0 基础 POC 基线](plans/v0.1.0-baseline.md)
- [v0.2.0 项目治理、完整报告与准入规则](plans/v0.2.0-report-and-governance.md)
- [v0.3.0 AI 风险分析与用例推荐](plans/v0.3.0-ai-risk-and-cases.md)
- [v0.4.0 模拟设备与自动化执行](plans/v0.4.0-simulated-device.md)
- [v0.5.0 音频与多模态分析](plans/v0.5.0-multimodal.md)
- [v1.0.0 真实设备与企业级版本准入](plans/v1.0.0-enterprise-release.md)

## 总体演进

```text
v0.1.0 基础测试执行与诊断 POC
    ↓
v0.2.0 完整报告与准入规则
    ↓
v0.3.0 AI 风险分析与用例推荐
    ↓
v0.4.0 模拟设备控制与自动化执行
    ↓
v0.5.0 音频与多模态分析
    ↓
v1.0.0 真实设备与企业级版本准入
```

## 版本规划

### v0.1.0：基础测试执行与诊断 POC

当前版本的定位是跑通可复现的基础闭环，不接入真实硬件。

核心模块：

- 任务配置、运行记录、队列、取消、重跑和异常中断恢复。
- 合成或导入视频、IMU、设备状态和日志数据。
- 视频、IMU、存储、资源和日志的确定性检查。
- 固定偏移、线性漂移和跨模态事件对齐分析。
- 人工检查结果、基础 HTML 报告和 ZIP 证据包。
- Mock/硅基流动诊断适配、证据引用校验和安全降级。
- Pytest、Allure 和 GitHub Actions CI 骨架。

明确边界：没有测试前 AI 用例推荐、ADB/HTTP/Shell 设备控制、音频采集、Jenkins 和真实模型效果验证。

### v0.2.0：完整报告与准入规则（已完成）

目标是把当前基础报告升级为可用于版本评审的测试交付物。

核心模块：

- 报告模板和统一的测试结论页面。
- 视频、IMU、资源和日志的趋势图、统计摘要和异常时间线。
- 不同版本、设备配置和测试运行之间的结果对比。
- 通过、失败、阻塞、未执行等状态的统一汇总。
- 质量门禁规则、失败阻断策略和可解释的准入原因。
- 报告、证据包和 CI 产物之间的版本与哈希关联。

预期验收：同一版本可以生成结构一致的报告；失败检查能够触发明确的准入失败；报告能够支持历史版本对比。

**结项状态**：2026-11-13 的 UI 精修已合并 `main`（`0286708`），前端全量测试 172 项通过、3 项原有跳过；用户随后确认 v0.2.0 收工，版本标记为完成。完成范围为已约定的项目治理、数据驱动模拟测试与事实报告链路，企业级强制质量准入不据此宣称已验收。历史未复验条目保留原证据状态。剩余 AI 开关、产品画像和人工批次优化见 v0.3.0；真实执行器后端见 v0.4.0。

### v0.3.0：AI 风险分析与测试用例推荐

目标是让 AI 参与测试前的分析，而不仅仅是运行后的诊断。

核心模块：

- 手动输入/粘贴需求与版本变更说明，结合项目级默认产品画像进行结构化分析；需求文件导入延后。
- AI 识别高风险功能、数据链路和潜在故障模式。
- 根据风险、历史失败和覆盖情况推荐测试类型与测试场景。
- 输出推荐理由、优先级、依赖条件和缺失信息。
- 将推荐结果转换为平台可执行的候选任务配置。
- 推荐结果的 Schema 校验、人工确认和版本化保存。

安全边界：AI 只提出建议，不直接修改测试事实、阈值或最终准入结论；确定性规则仍负责正式检查。

### v0.3.0 补充：AI 能力统一开关（P0）

验收反馈指出"首页两个入口不决定 AI 是否启用"是错的。下一版要求：

- 「开启平台」且 AI 配置可用 → 全部 AI 功能走真实模型；
- 「暂不配置，进入平台」→ 全局关闭 AI，所有 AI 入口统一提示"AI 已关闭"；
- 顶部常驻显示当前模式：`AI：已开启（服务商/模型）` 或 `AI：已关闭`；
- 顶栏提供直接开启/关闭 AI 的按钮，不需要返回首页；关闭时人工、规则转换、确定性测试和事实报告照常使用；
- 后端用一个全局设置项控制，各 AI 服务统一读取，不再各自判断。

### v0.3.0 补充：产品画像（P0）

新建项目时填写被测产品形态（实体按键、指示灯、摄像头、麦克风、提示音、通信接口、测试环境、测试平台），用于：

- AI 判断用例能否自动化；
- 最终报告开头描述"测的是什么"；
- 已有项目需要补"编辑画像"入口。
- 不做版本级画像覆盖；版本新增或变化的硬件能力直接在测试需求中补充文字，作为本次 AI 分析上下文。

**开发顺序**：全局 AI 开关与产品画像 → 结构化需求与风险分析 → 用例推荐 → 人工审核与版本保存 → 纳入现有用例/测试组 → 历史结果驱动回归建议。智能回归建议、人工批次附件继承及人工/自动化关联提示作为本版 P1 交付；需求导入预留入口另行独立验收。详细范围以 [v0.3.0 开发计划](plans/v0.3.0-ai-risk-and-cases.md) 为准；真实执行器接入不提前到本版。

v0.3.0 每个开发项必须有独立可运行的入口、固定验收数据、人工操作步骤、明确预期与证据；单项验收通过后方可继续后续依赖任务。具体拆分及待确认需求见该版本开发计划。

### v0.3.0 范围裁决：需求文件导入延后

本版使用手动输入/粘贴的需求文字和版本变更说明，保留需求、风险与用例审核。需求文件导入及自动解析暂不实现，但保留正常外观的按钮，点击时仅弹出“该功能开发中”，不出现常驻未开发说明，不产生任何导入或解析副作用；既有正式用例表导入不受影响。实际开发安排在 v0.4.0 之后，具体版本待定。

### v0.4.0：模拟设备控制与自动化执行

目标是让候选测试用例能够驱动一个可控的模拟设备执行。

核心模块：

- ADB 控制适配器：连接、启动、停止、状态查询和命令执行。
- HTTP 控制适配器：设备 API、健康检查和故障注入接口。
- Shell 控制适配器：受限命令白名单、超时、退出码和日志采集。
- 统一设备控制接口，隔离 ADB、HTTP 和 Shell 的具体实现。
- 用例步骤、前置条件、执行结果和设备日志的关联。
- 控制失败重试、超时、取消和设备状态恢复。

预期验收：同一测试用例可以通过统一接口切换不同模拟设备；每条控制命令都有结果、日志和超时证据。

### v0.4.0 补充：执行器与可执行用例（2026-11 验收后确定）

v0.2.0 的人工验收确认了"自动化不能只有模拟执行"，下一个版本按下面的方向落地。

**三种执行器（项目级配置，测试组从中选择）**

| 类型 | 平台做什么 | 结果怎么拿 |
| --- | --- | --- |
| 本地框架 | 把选中的用例导出成 `cases.json`，调用项目入口命令 | 读取框架写出的 `results.json` |
| Jenkins | 填地址 + 任务名 + 令牌，触发构建 | 轮询构建状态，完成后抓测试报告 |
| GitHub CI | 填 owner/repo + workflow + 令牌，`workflow_dispatch` | 轮询 run 状态，完成后下载 artifact |

统一约束：

- 执行器挂在**项目级**，多个测试组可以共用同一个执行器，触发时把测试组、用例集、数据包作为参数传入；
- 令牌不落明文，只存引用或加密字段；
- 执行前统一预检：用例已校验、数据包已分配、执行器连接正常。

**可执行用例的生成与审核**

```
选执行器 → 选用例 + 数据包 → 生成 cases.json
→ 结构校验（必须通过）→ 人工审核（可选跳过）→ 发布版本 → 执行 → 结果回写
```

- 结构校验：字段齐全、用例 id 有效、数据包路径存在；
- 人工审核：默认要求看一眼，允许勾选"我已确认，跳过逐条审核"；
- 发布后的 JSON 锁定版本，改用例必须重新生成。

**文件契约（第一版）**

```json
// cases.json
{
  "group": "智能硬件图像测试",
  "runner": "本地 pytest 框架",
  "format": "platform",
  "cases": [
    { "case_number": "AUTO-000001", "package": "DP-000001",
      "assert": { "metric": "frame_rate", "op": ">=", "value": 30 } }
  ]
}
```

```json
// results.json
{ "results": [
  { "case_number": "AUTO-000001", "status": "passed",
    "actual": { "frame_rate": 30.2 } }
] }
```

### v0.5.0：音频与多模态分析

目标是将音频纳入现有的视频、IMU、资源和日志分析链路。

核心模块：

- 音频采集、编码、采样率和时长检查。
- 音频断续、静音、削波和噪声等基础质量检查。
- 音频事件与视频帧、IMU 峰值、设备日志的时间对齐。
- 跨模态异常窗口和关联证据展示。
- 多模态证据包大小控制、脱敏和报告导出。
- 音频异常与视频/IMU 异常的组合场景。

预期验收：音频异常可以被独立检测，也可以在同一时间窗口内与其他模态进行确定性关联；不能仅凭时间相关性宣称根因。

### v0.4.0 之后的待规划事项（具体版本待定）

- 测试需求文件导入与解析：需求文档上传、文件格式兼容、原文追溯、AI 解析与结构化提取，以及导入错误处理。待执行器阶段之后再规划与开发，不纳入 v0.3.0 或 v0.4.0，也不默认挤占 v0.5.0 的音频与多模态范围。后续须单独 To Spec、拆票和人工验收。

### v1.0.0：真实设备与企业级版本准入

目标是从本地演示 POC 发展为可接入真实硬件和企业 CI 的测试平台。

核心模块：

- 真实设备适配器、设备发现、连接管理和能力探测。
- 真实采集链路、设备资源指标和现场日志采集。
- 设备固件/软件版本管理和兼容性矩阵。
- 版本回归选择、历史结果追踪和失败趋势分析。
- GitHub Actions 正式质量门禁和 Jenkins 对照流水线。
- 测试结果、报告和证据包的正式版本准入。
- 权限、凭据隔离、审计记录和企业部署配置。

正式准入原则：模型只能提供辅助分析；设备控制、确定性检查、质量门禁和最终准入必须保留可复查的工程证据。

## 版本边界

以下内容不应在 v0.1.0 阶段对外宣称已经完成：

- AI 测试前风险分析和测试用例推荐。
- ADB、HTTP、Shell 或其他真实/模拟设备控制。
- 音频、蓝牙和真实 MCAP 数据链路。
- 完整报告模板、版本对比和企业级质量门禁。
- Jenkins 流水线和真实模型线上效果。

每个版本完成后，应同步更新 [首版验收清单](v1-acceptance-checklist.md)、[课程映射](course-coverage.md) 和 [面试案例](interview-case.md)，并为已完成项补充测试或产物证据。
